## 1. 从零跑起来（5 步）

### 1.1 前置条件

| 需要 | 说明 |
|---|---|
| **Node.js** | 跑 Vite / 守卫 / wrangler（建议 20+） |
| **pnpm** | 本项目用 pnpm（**不是 npm/yarn**）：`npm i -g pnpm` |
| **Cloudflare 账号**（可选） | 只有"部署"才需要；本地开发**不需要** |

### 1.2 五步

```bash
# ① 进工作区根（注意：不是 sudoku/ 里面）
cd "c:/Users/lenovo/Desktop/学习资料/vue3"

# ② 装依赖（根目录装，三个子项目共享）
pnpm install

# ③ 起"后端"（另一个终端窗口，保持运行）
cd sudoku
npx wrangler pages dev        # 同时伺服 dist + 跑 functions/ + 本地 D1；默认 8788 端口

# ④ 起前端（再开一个终端）
cd sudoku
pnpm dev                      # Vite，默认 5173；/api 代理到 8788

# ⑤ 打开浏览器
#    http://localhost:5173
```

**为什么是"两个终端"**：前端（Vite）与后端（wrangler）是**两个进程**（两个端口，5773↔8788 用代理连起来）。

### 1.3 两种后端模式（`.env.local` 决定）

```bash
# sudoku/.env.local
API_TARGET=https://sudoku-game-bo0.pages.dev
```
| 情况 | `/api` 请求打到 | 数据 | 什么时候用 |
|---|---|---|---|
| **有这行** | **线上后端**（Pages 部署） | **线上 D1 数据** | 只改前端、想用真实数据 |
| 注释/删掉 | 本地 `127.0.0.1:8788`（wrangler） | 本地 D1 | 要改后端 / 不想动线上数据 |

**注意**：`.env.local` **已被 `.gitignore` 忽略**（不进仓库）→ 换机器后它是**不存在**的 → 默认走本地后端。
> **判断当前连的是哪个后端**：看浏览器 Network 面板里 `/api/me` 的**域名**。

### 1.4 本地数据库（D1）怎么建表

后端第一次跑起来时，本地 D1 是**空数据库**（没有表）→ 需要应用 `schema.sql`：
```bash
npx wrangler d1 execute sudoku-db --local --file=schema.sql
```
`schema.sql` 是**幂等**的（`CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS`）→ **重复跑安全**。

## 2. 命令逐条（**每条都讲清楚它干了什么**）

### 2.1 常用七条（`sudoku/package.json`）

| 命令 | 实际执行 | 干什么 | 什么时候跑 |
|---|---|---|---|
| `pnpm dev` | `vite` | 起开发服务器（HMR 热更新） | 写代码时 |
| `pnpm guard` | `node scripts/check-arch.mjs` | **架构守卫**（R1~R15），违规 exit 1 | **每次提交前** |
| `pnpm typecheck` | `vue-tsc --noEmit -p tsconfig.app.json` | 前端类型检查（含 `.vue`） | 改完前端代码 |
| `pnpm typecheck:functions` | `tsc --noEmit -p functions/tsconfig.json` | 后端类型检查 | 改完 `functions/` |
| `pnpm build` | `vue-tsc -b` && `tsc --noEmit -p functions/tsconfig.json` && `vite build` | 三段式构建（**不含守卫**） | 发布前 |
| `pnpm preview` | `vite preview` | 本地预览 `dist/`（静态服务器） | 想验证产物 |
| `pnpm format` | `prettier --write "src/**/*.{ts,vue,css}"` | 格式化源码 | 提交前（可选） |

**三条最容易搞混的**：
1. **`build` 不含 `guard`**（`ARCHITECTURE.md` 顶部专门写了：*"`pnpm build` 不含它，guard 单独跑"*）→ **发布前要手动跑 `pnpm guard`**；
2. **`typecheck` 与 `build` 的第一步重复**（都是 `vue-tsc`）—— `typecheck` 是"只想检查不想打包"时的快捷方式；
3. **`preview` 预览的是"已构建产物"**（`dist/`），**不是**开发服务器 → 用它验证"打包后有没有问题"（例如生产环境才出现的代码）。

### 2.2 后端与数据库命令（wrangler）

| 命令 | 干什么 |
|---|---|
| `npx wrangler pages dev` | **本地起后端**（`dist/` 静态 + `functions/` + 本地 D1），默认 **8788** |
| `npx wrangler d1 execute sudoku-db --local --file=schema.sql` | 对**本地** D1 应用表结构 |
| `npx wrangler d1 execute sudoku-db --remote --file=schema.sql` | 对**线上** D1 应用表结构（部署时用） |
| `npx wrangler d1 execute sudoku-db --local --command "SELECT * FROM user LIMIT 5"` | 查本地库（调试用） |
| `npx wrangler types` | 生成/更新 `worker-configuration.d.ts`（Cloudflare 绑定类型） |
| `npx wrangler pages deploy dist` | 部署（§6） |

**`--local` / `--remote` 是最容易搞混的一对**：
- `--local`：数据在 `.wrangler/` 里（本机，已被 gitignore）；
- `--remote`：**动的是线上真实数据**（危险操作，小心）。

### 2.3 工作区（根）命令

| 命令 | 干什么 |
|---|---|
| `pnpm install` | 装/还原所有子项目的依赖（**必须在根执行**） |
| `pnpm dev:sudoku` | = `pnpm --filter sudoku dev`（在根直接起数独的前端） |
| `pnpm --filter sudoku add <包>` | 给数独加一个依赖（自动改 `sudoku/package.json` 与根 lockfile） |
| `pnpm --filter sudoku <script>` | 在根执行数独的任意脚本（例：`pnpm --filter sudoku guard`） |

### 2.4 一条"提交前"的标准流水线（建议照做）

```bash
cd sudoku
pnpm guard && pnpm typecheck && pnpm typecheck:functions && pnpm build
```
**为什么要四条都跑**：
| 命令 | 拦住的 |
|---|---|
| `guard` | 越层依赖 / 页面太肥 / core 不纯 / 桶文件 …（R1~R15） |
| `typecheck` | 前端类型错（含 `.vue` 模板里的类型） |
| `typecheck:functions` | 后端类型错（**与前端是两套 tsconfig**） |
| `build` | 打包期问题（例如 `import` 路径大小写、动态导入路径错） |

> **`build` 已经包含后两条里的两条**（它内部就跑了两个 tsc），所以实际最短可以写成：
> `pnpm guard && pnpm build` —— **但把四条列出来更清楚**（知道每一步在拦什么）。

## 3. 配置文件逐个讲

### 3.1 `sudoku/package.json`（全文 31 行）

```json
{
  "name": "sudoku",
  "private": true,
  "version": "0.0.0",
  "type": "module",
  "scripts": { …见 §2.1… },
  "dependencies": {
    "pinia": "^4.0.3",
    "vue": "^3.5.42",
    "vue-router": "^5.3.1"
  },
  "devDependencies": {
    "@cloudflare/workers-types": "^5.20261009.1",
    "@types/node": "^24.13.3",
    "@vitejs/plugin-vue": "^6.0.8",
    "@vue/tsconfig": "^0.9.1",
    "prettier": "^3.9.9",
    "typescript": "~6.0.2",
    "vite": "^8.3.0",
    "vite-plugin-vue-devtools": "^8.2.1",
    "vue-tsc": "^3.3.11",
    "wrangler": "^4.149.0"
  }
}
```

| 字段 | 值 | 含义 |
|---|---|---|
| `private: true` | — | **不会被误发布到 npm**（"这是个应用，不是库"） |
| `type: "module"` | — | 本包的 `.js` 按 **ESM** 解析（00 册 §1.3） |
| `dependencies` | vue / pinia / vue-router | **运行时会打进产物**的三样（项目只用了这三样！） |
| `devDependencies` | 10 个 | 只在开发/构建期用 |

**`dependencies` 只有三个 —— 值得注意**：
| 包 | 作用 | 为什么是"必需的" |
|---|---|---|
| `vue` | 框架本体 | — |
| `pinia` | 状态管理（05 册） | 三个 store |
| `vue-router` | 路由 | 13 个页面 |

**没有 axios**（R2 全局禁 → 统一 `fetch`）、**没有 UI 库**（组件全自写）、**没有工具库**（`core/` 自己写）。
> **"依赖越少，越不会被别人的升级拖着走"** —— 这也是本项目能把"五层架构 + 守卫"讲清楚的前提。

**`devDependencies` 逐个**：

| 包 | 谁在用 | 说明 |
|---|---|---|
| `vite` | `pnpm dev` / `build` | 构建工具（00 册 §2.3） |
| `@vitejs/plugin-vue` | `vite.config.ts` | 让 Vite 能编译 `.vue` |
| `vite-plugin-vue-devtools` | `vite.config.ts` | Vue DevTools 的增强面板（开发时用） |
| `typescript` | `tsc` | 类型检查器（`~6.0.2` 表示只升补丁版） |
| `vue-tsc` | `pnpm typecheck` / `build` | **懂 `.vue` 的 tsc** |
| `@vue/tsconfig` | `tsconfig.app.json` 的 `extends` | Vue 官方推荐的 TS 配置（**它是依赖包，不是项目文件** —— 00 册 §2.4 的常见误会） |
| `@cloudflare/workers-types` | `functions/tsconfig.json` 的 `types` | 后端的 `D1Database` / `PagesFunction` 类型（**没有它后端全是红波浪线**） |
| `@types/node` | `tsconfig.node.json` | 让 `vite.config.ts` 里的 `path`/`process` 有类型 |
| `wrangler` | §2.2 的命令 | Cloudflare 官方 CLI |
| `prettier` | `pnpm format` | 代码格式化 |

**版本号前缀（`^` / `~`）的含义**：
| 写法 | 允许升级的范围 | 例 |
|---|---|---|
| `^4.0.3` | **主版本内**任意（4.x.x） | pinia |
| `~6.0.2` | **只升补丁**（6.0.x） | typescript（**故意更保守**：TS 小版本也可能带来新报错） |
| 无前缀 | 锁死 | — |

> **实际装的版本记录在根 `pnpm-lock.yaml`**（00 册 §1.4）→ 换机器 `pnpm install` 会装出**完全一样**的版本。

### 3.2 `vite.config.ts`（全文 24 行）

```ts
import vue from '@vitejs/plugin-vue'
import path from 'path'
import { defineConfig, loadEnv } from 'vite'
import vueDevTools from "vite-plugin-vue-devtools";

// https://vite.dev/config/
export default defineConfig(({ mode }) => {
  // 本机联调的后端地址：环境变量 API_TARGET > .env.local > 默认本地 Functions
  const env = loadEnv(mode, process.cwd(), '')
  return {
    plugins: [vue(), vueDevTools()],
    base: './',
    resolve: {
      alias: {
        "@": path.resolve("./src")
      }
    },
    server: {
      // 默认：本地后端 127.0.0.1:8788（npx wrangler pages dev）
      // 直连线上后端（用线上数据）：.env.local 里写 API_TARGET=https://xxx.pages.dev
      proxy: { '/api': env.API_TARGET || 'http://127.0.0.1:8788' },
    },
  }
})
```

**逐行**：

| 行 | 作用 | 为什么 |
|---|---|---|
| `defineConfig(({ mode }) => { … })` | **用函数形式的配置** | 因为要读 `mode`（`development` / `production`）来决定代理 |
| `loadEnv(mode, process.cwd(), '')` | 读 `.env*` 文件 | 第三个参数 `''` = **不加前缀过滤**（默认只暴露 `VITE_` 开头的变量；这里要读 `API_TARGET`，所以放开） |
| `plugins: [vue(), vueDevTools()]` | 编译 `.vue` + 开发面板 | — |
| `base: './'` | 产物用**相对路径**引用资源 | 部署到子路径（如 `https://xxx.pages.dev/sudoku/`）时也能加载 |
| `resolve.alias { "@": …/src }` | **路径别名的"打包侧"配置** | 与 `tsconfig.app.json` 的 `paths` **必须一致**（00 册 §2.5） |
| `server.proxy '/api'` | 开发时把 `/api/*` 转发到后端 | **避免 CORS**（浏览器以为同源）；线上是同源部署，不需要代理 |

**两个"如果忘了会怎样"**：
- **忘了 `alias`**：TS 不报错（`paths` 管类型），但**打包时找不到 `@/…`** → `Failed to resolve import "@/components/…"` → **所以别名要配两处**；
- **忘了 `proxy`**：开发时请求 `/api/me` 会打到 **Vite 自己（5173）** → 返回 `index.html` → 前端报 **"接口不存在或服务异常"**（08 册 §4.3 那条非 JSON 检查就是为这种时候准备的）。

**`base: './'` 的一个细节**：产物里的资源引用变成 `./assets/xxx.js`（相对），所以 `dist/` 放在任意路径都能跑。
> **但要注意**：它也让"深链接刷新"更像静态服务器的事 —— 所以 `wrangler pages dev` 与 Pages 平台**都要能以 `index.html` 兜底**（SPA 行为）。

### 3.3 `wrangler.toml`（逐行，运维视角）

```toml
name = "sudoku-game"                    # 项目名（部署到 Cloudflare 时的名字）
pages_build_output_dir = "dist"         # 前端静态产物在哪 → wrangler pages dev 同时伺服 dist + functions
compatibility_date = "2026-10-11"       # Workers 运行时的"API 版本日期"

[[d1_databases]]
binding = "DB"                          # ★ 代码里访问数据库的变量名：env.DB
database_name = "sudoku-db"             # 云端库名
database_id = "caeffb49-..."            # 云端库 id
```

| 行 | 作用 | 注意 |
|---|---|---|
| `name` | 部署后的项目名 | 也决定线上域名（`<name>.<account>.pages.dev`） |
| `pages_build_output_dir` | 告诉 wrangler"静态产物在哪" | **`wrangler pages dev` 会同时伺服 `dist/`（静态）+ `functions/`（接口）** |
| `compatibility_date` | **运行时行为锁** | 写死它，Cloudflare 日后升级不会改变你的代码行为（02 册 §1.3） |
| `binding = "DB"` | **必须与 `functions/types.ts` 的 `Env.DB` 同名** | 改一处就要改三处（toml / types.ts / 代码） |
| `database_id` | 线上库 id | 本地开发用不上（本地 D1 在 `.wrangler/` 里） |

**⚠️ 一个容易忽略的点**：`database_id` 在本机看着"没用"，但**部署时必须是真实存在的库 id** —— 否则 Pages 部署后 `/api/*` 会因为"绑定找不到"而 500。
**部署前检查清单**：`npx wrangler d1 list` 能看到 `sudoku-db` 且 id 与 toml 一致。

### 3.4 四个 `tsconfig` 逐项（**每个选项都在拦什么**）

#### (1) `tsconfig.json`（总入口，6 行）

```json
{
  "files": [],
  "references": [
    { "path": "./tsconfig.app.json" },
    { "path": "./tsconfig.node.json" }
  ]
}
```
- **`files: []`**：这个文件**自己不含任何文件** —— 它只是"项目引用（project references）"的**入口**；
- **`references`**：把两个子配置拼起来 → 编辑器（VS Code）能同时用两套规则；
- **为什么要有它**：让 `vue-tsc -b`（build 模式）能"按引用去构建两个子项目"（`-b` 就是"构建引用项目"的意思）。

#### (2) `tsconfig.app.json`（前端，最关键）

```json
{
  "extends": "@vue/tsconfig/tsconfig.dom.json",
  "compilerOptions": {
    "paths": { "@/*": ["./src/*"] },
    "tsBuildInfoFile": "./node_modules/.tmp/tsconfig.app.tsbuildinfo",
    "types": ["vite/client"],
    "allowArbitraryExtensions": true,
    "noUnusedLocals": true,
    "noUnusedParameters": true,
    "erasableSyntaxOnly": true,
    "noFallthroughCasesInSwitch": true
  },
  "include": ["src/**/*.ts", "src/**/*.tsx", "src/**/*.vue"]
}
```

| 项 | 作用 | 为什么 |
|---|---|---|
| `extends: @vue/tsconfig/tsconfig.dom.json` | 继承 Vue 官方的 **DOM 环境**配置 | 里面已经开好 `strict`、`moduleResolution: bundler` 等（**这个文件属于依赖包**） |
| `paths { "@/*" }` | **类型检查侧的别名** | 与 `vite.config.ts` 的 `alias` 配对（少一个就出问题） |
| `tsBuildInfoFile` | 增量构建的缓存文件 | 放 `node_modules/.tmp`（**不进仓库**） |
| `types: ["vite/client"]` | 引入 Vite 的全局类型 | 于是 `import.meta.env.DEV` / `import.meta.url` 有类型（01 册 §3.8、08 册 §8 都用到了） |
| `allowArbitraryExtensions` | 允许 `import './x.css'` 这类任意后缀 | 项目里有 `.css` 导入 |
| **`noUnusedLocals`** | 未使用的变量 → **报错** | 这就是"删了模板分支就要删 import"的原因（00 册 §2.6 的 TS6133） |
| **`noUnusedParameters`** | 未使用的参数 → **报错** | 所以要用不到的参数必须写成 `_`（00 册 §4.9 的约定） |
| `erasableSyntaxOnly` | 只允许"可擦除"的 TS 语法 | 即"编译后能完全删掉的语法"（不允许 `enum`、`namespace` 这类会产出运行时代码的）→ 与"构建器直通"更安全 |
| `noFallthroughCasesInSwitch` | `switch` 分支不许"漏 break" | 防止意外穿透 |
| `include` | 只检查 `src/**` | **不含 `functions/`**（那是另一个 tsconfig）与 `vite.config.ts`（node 那个） |

#### (3) `tsconfig.node.json`（只给 `vite.config.ts` 用）

```json
{
  "compilerOptions": {
    "tsBuildInfoFile": "./node_modules/.tmp/tsconfig.node.tsbuildinfo",
    "target": "es2023",
    "lib": ["ES2023"],
    "types": ["node"],
    "skipLibCheck": true,
    "module": "nodenext",
    "allowImportingTsExtensions": true,
    "verbatimModuleSyntax": true,
    "moduleDetection": "force",
    "noEmit": true,
    …同上的四条 lint 项…
  },
  "include": ["vite.config.ts"]
}
```
| 项 | 为什么 |
|---|---|
| `types: ["node"]` | `vite.config.ts` 里用了 `path` / `process` → 需要 Node 类型 |
| `lib: ["ES2023"]`（无 DOM） | 这个文件**跑在 Node 里**，不该用 DOM API |
| `module: nodenext` + `moduleDetection: force` | 按 Node 的 ESM 规则解析（`package.json` 是 `type: module`） |
| `skipLibCheck: true` | 不检查依赖包里的 `.d.ts`（**大幅提速**，也避免别人的类型 bug 干扰你） |
| `noEmit: true` | 只检查不产出（Vite 自己会执行这个配置） |
| `include: ["vite.config.ts"]` | **只管这一个文件** |

#### (4) `functions/tsconfig.json`（后端）

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "lib": ["ES2022", "DOM", "DOM.Iterable"],
    "module": "ESNext",
    "moduleResolution": "Bundler",
    "types": ["@cloudflare/workers-types"],
    "strict": true,
    "skipLibCheck": true,
    "noEmit": true,
    "verbatimModuleSyntax": true
  },
  "include": ["**/*.ts"]
}
```
| 项 | 为什么 |
|---|---|
| `types: ["@cloudflare/workers-types"]` | 提供 `D1Database` / `PagesFunction` / `Response`… |
| **`lib` 里有 `DOM`** | **虽然跑在 Worker 里，但 Web 标准 API（`fetch`/`Response`/`crypto`/`TextEncoder`）与 DOM 类型是同一套** → 借用 DOM lib 来拿到这些类型 |
| `moduleResolution: Bundler` | 与 esbuild（wrangler 的打包器）一致 |
| `strict: true` | 后端也开严格模式 |
| **没有 `paths`**（重要） | **所以后端只能用相对路径** import core（`../../src/core/...`）—— 03 册 §3.3、08 册 §1.2 都提到这条 |
| `include: ["**/*.ts"]` | 只含 `functions/` 下的文件（**注意：它不会去检查 `src/`** —— 但 import 进来的文件会被连带检查） |
| `verbatimModuleSyntax` | 与前端一致：类型导入必须 `import type` |

### 3.5 其余工程文件（一表看全）

| 文件/目录 | 是什么 | 要不要进仓库 | 注意 |
|---|---|---|---|
| `index.html` | **SPA 的唯一 HTML**（Vue 挂载点 `<div id="app">`） | ✅ | 里面只有一个 `<script type="module" src="/src/main.ts">` |
| `src/main.ts` | 应用入口（建 app → 装 pinia/router → 挂载） | ✅ | 01 册 §2.1 |
| `public/` | **原样拷到 `dist/` 的静态文件**（如 `favicon.ico`） | ✅ | 这里的东西**不经打包**（不能 import） |
| `worker-configuration.d.ts` | `npx wrangler types` 生成的 **Cloudflare 绑定类型** | ✅（可生成） | 改 `wrangler.toml` 后重新生成 |
| `schema.sql` | **数据库表结构**（5 张表 + 索引） | ✅ | 幂等；本地/线上各应用一次 |
| `scripts/check-arch.mjs` | **架构守卫脚本** | ✅ | 03 册 §5 逐段解剖过 |
| `.env.local` | 本机联调的后端地址（`API_TARGET`） | ❌（gitignore） | **换机器后不存在** → 默认走本地后端 |
| `.dev.vars` | wrangler 的**本地 Secrets**（如本地的 `SESSION_SECRET` 之类） | ❌（gitignore） | 只在本地 `wrangler pages dev` 用 |
| `.wrangler/` | **本地 D1 的数据文件** | ❌（gitignore） | 删了 = 本地库空了（要重新 apply schema.sql） |
| `dist/` | 构建产物 | ❌（gitignore） | `pnpm build` 生成 |
| `node_modules/` | 依赖 | ❌ | `pnpm install` 生成 |

**`.gitignore` 里值得注意的三条**：
```
*.local          ← 覆盖 .env.local
.wrangler/       ← 本地 D1
.dev.vars        ← 本地密钥
```
> **"什么该进仓库"的原则**：**能由命令重新生成的、或含本机/机密信息的，都不进**（依赖、产物、缓存、密钥、本地数据库）。
> 所以换机器后的"从零跑起来"就是 §1 那五步 —— **每个被忽略的东西都有对应的命令把它造出来**。

## 4. 调试手段（按"问题类型"选工具）

### 4.1 界面不对 → Vue DevTools

**打开方式**：装浏览器扩展（Vue.js devtools），或直接用项目自带的 `vite-plugin-vue-devtools`（开发时页面下方有悬浮球，点开是内置面板）。

| 面板 | 看什么 |
|---|---|
| **Components** | 组件树、每个组件的 **props / setup 变量**、事件（`emits` 日志） |
| **Pinia** | **三个 store 的完整状态 + 时间轴**（谁改了、改前改后） |
| **Timeline** | 事件 / 组件渲染 / 路由 / 性能（**看"点了之后到底触发了哪些重渲染"**） |

**最常用的三个动作**：
1. **改 state 看界面**：在 Pinia 面板里直接把 `game.selected` 改成 `[0,0]` → 看画布有没有反应（一秒判断"是渲染问题还是数据问题"）；
2. **看 props**：选中 `BoardView` → 看 `board`/`selected`/`zoom` 是不是你以为的值（链路排查 §2.1 的第①②步）；
3. **看事件**：Components 面板的事件页，点一下按钮看 `emit` 有没有发出去。

### 4.2 请求不对 → 浏览器 Network 面板

| 看什么 | 怎么判断 |
|---|---|
| **域名** | `/api/me` 是打到 `127.0.0.1:8788` 还是线上？→ 判断 `.env.local` 生效没（§1.3） |
| **状态码** | 401（登录态）/ 403（越权）/ 404（不存在或不可见）/ 429（限流）—— 08 册 §4.3 的四出口 |
| **Response** | 后端返回的 `{ error: '…' }` 文案（前端就是拿它显示的） |
| **Request Headers** | `Authorization: Bearer …` 有没有带上（没带 → `auth: false` 或 token 没存） |
| **Payload** | POST/PATCH 的 body 是不是你以为的（例如 `mine: 1`、`limit/offset`） |
| **content-type** | 是不是 `application/json`（**返回 `text/html` 说明打到 `index.html` 了** → 路径写错） |

> **"请求 200 但界面没数据"** 的经典原因：**看的是缓存的响应**（Network 面板勾了 "Disable cache" 再试）。

### 4.3 状态不对（但看不出谁改的）→ Pinia 时间轴 + 断点

1. **Pinia 面板**：按时间倒序看"最近改了哪些 state"（一眼看出是哪个动作改的）；
2. **在 store 的动作里打断点**：DevTools → Sources → 找到 `stores/game.ts` → 在 `inputNum` 里打断点 → 看调用栈（**谁调用了它**）；
3. **`debugger` 语句**：临时插一句 `debugger`（比 console.log 更精准，能看整条调用栈）。

### 4.4 Worker 出问题 → 专门的调试法

| 手段 | 说明 |
|---|---|
| **在 `worker.ts` 里 `console.log`** | Worker 的日志**会出现在页面的 Console 里**（但要看清前缀，Chrome 会标出来自 worker） |
| **Sources 面板 → worker** | Chrome 的 Sources 里能找到 `xxx.ts` 这个 worker 脚本 → **可以直接在里面打断点** |
| **看 `workerClient` 的超时文案** | 一直转圈然后显示"生成超时" → 说明 Worker 在跑但没回来（`generator` 太难 / 死循环） |
| **临时把 Worker 换成同步调用** | 在 `useDifficultyFlow` 里直接调 `generatePuzzle`（丢掉 Worker）→ 如果这样能出题，问题在通信而不在算法 |

### 4.5 架构问题 → 守卫脚本

```bash
pnpm guard
```
它报的每一条都是"**某个文件违反了某条红线**"（R1~R15）→ 报错信息里会写**规则名 + 文件 + 行号 + 怎么改**（03 册 §5 逐段解剖过它）。
**它是"最容易定位的一类问题"** —— 因为报错已经告诉你怎么改了。

### 4.6 类型问题 → `pnpm typecheck`

| 报错特征 | 说明 |
|---|---|
| `TS6133: 'xxx' is declared but its value is never read` | 未使用的变量（`noUnusedLocals` / `noUnusedParameters`），**删掉或加 `_` 前缀** |
| `TS2339: Property 'x' does not exist on type 'Y'` | 类型里没这个属性（契约没写对 / 拼错） |
| `TS2345: Argument of type 'X' is not assignable to parameter of type 'Y'` | 传参类型不匹配（**最常见的是 `string \| number` 要收窄**，07 册 §12.3 的 `as number`） |
| `TS2532: Object is possibly 'undefined'` | 严格模式下的可能空值 → 用 `?.` 或先判断 |
| 报错在 `.vue` 文件里 | 说明是 `vue-tsc` 报的（`tsc` 看不懂 `.vue`） |
| **前端不报、后端报** | 用错 tsconfig 了：后端要 `pnpm typecheck:functions` |

### 4.7 一条"调试决策树"（遇到问题先看这张）

```
问题在哪？
├─ 界面不对
│   ├─ 数据对吗？（Pinia 面板） ── 不对 → 查 composable 的动作（断点）
│   └─ 数据对但界面不对 ────────── 查响应式（computed / watchEffect / props）
├─ 请求不对（Network 面板）
│   ├─ 没发出去 ────────────── 查事件绑定 / v-if / loading 守卫
│   ├─ 4xx ──────────────── 看后端返回的 error 文案
│   └─ 打到 index.html（content-type: text/html） → 路径错了
├─ 构建/类型报错
│   ├─ guard 报错 ──────────── 按它说的改（最明确）
│   └─ tsc 报错 ────────────── 看是不是用错了 tsconfig
└─ 跑不起来（红屏 / 白屏）
    ├─ Console 有 JS 错 ─────── 按栈顶的文件去看
    └─ 什么都没有 ──────────── 看 Network：资源 404？（base/alias 配错）
```

| # | 报错 | 违反了 | 怎么办 |

## 6. 发布（Cloudflare Pages + D1）

### 6.1 首次发布（六步，**只需做一次前四步**）

```bash
# ① 登录 Cloudflare（浏览器授权）
npx wrangler login

# ② 建 D1 库（记下输出里的 database_id）
npx wrangler d1 create sudoku-db

# ③ 把 database_id 填进 wrangler.toml 的 [[d1_databases]]
#    （不填 → 部署后 /api/* 全 500）

# ④ 对线上库应用表结构（注意是 --remote）
npx wrangler d1 execute sudoku-db --remote --file=schema.sql

# ⑤ 构建（先过守卫与类型）
pnpm guard && pnpm build

# ⑥ 部署
npx wrangler pages deploy dist --project-name sudoku-game
```

### 6.2 发布后验证清单（**五项，缺一不可**）

| 项 | 怎么验 |
|---|---|
| ① 首页能开 | 打开 `https://<项目>.pages.dev` |
| ② 接口通 | 看 Network 里 `/api/me` 返回 **200/401**（不是 500、不是 HTML） |
| ③ **深链接刷新** | 直接访问 `/p/xxxx` 再刷新 → 应该正常（Pages 的 SPA 兜底） |
| ④ 数据库写入 | 注册一个账号 → 出题一次 → 在「我的题目」看到它 |
| ⑤ 静态资源 | Console 无 404（`base: './'` 生效） |

**③ 是最容易漏的一项**：SPA 的路由（`/p/:pid`）在真实服务器上需要"任何未命中的路径都回 `index.html`"—— Cloudflare Pages **默认对单页应用有兜底**，但如果加了 `_redirects`/`_routes.json` 就要自己确认。

### 6.3 日常更新流程（改了代码之后）

```bash
pnpm guard && pnpm build
npx wrangler pages deploy dist --project-name sudoku-game
```
- **前端改动**：就这样（产物名带哈希 → 缓存天然失效）；
- **后端改动**（`functions/`）：**同一份部署里带上**（`functions/` 会被打包进这次部署）；
- **数据库结构改动**：改 `schema.sql`（保持幂等）→ `npx wrangler d1 execute sudoku-db --remote --file=schema.sql`。

### 6.4 回滚与查看

| 想做什么 | 怎么做 |
|---|---|
| 回到上一个版本 | Cloudflare Dashboard → Pages → 项目 → Deployments → 选历史版本 → **Rollback** |
| 看线上日志 | Dashboard → Pages → 项目 → Functions → **实时日志**（`console.log` 都在） |
| 查线上数据 | `npx wrangler d1 execute sudoku-db --remote --command "SELECT COUNT(*) FROM puzzle"` |
| 查本地数据 | 把 `--remote` 换成 `--local` |

> **⚠️ 一条铁律**：**`--remote` 动的是真实用户数据**。执行任何 `UPDATE` / `DELETE` 之前，先用 `SELECT` 看一眼要影响哪些行。

> **把"算"、"记"、"编排"、"画"、"和外界打交道"这五件事彻底分开，并且用一台机器（`pnpm guard`）守着这条分界线不被打穿。**

**这套方法可以原样搬到任何项目上**（不只是数独、不只是 Vue）：
- 遇到"一个文件越来越长" → 问"它是不是同时在做两件事"；
- 遇到"改一处坏三处" → 问"这个依赖方向是不是反了"；
- 遇到"new 需求加不动" → 问"新代码该落在哪一层"。
