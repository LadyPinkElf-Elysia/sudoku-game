## 1. 后端运行环境：这个项目的"后端"是什么

### 1.1 知识点：三种"后端"形态，本项目是第三种

| 形态 | 长什么样 | 特点 |
|---|---|---|
| 传统服务器 | Node/Java 常驻进程 + Nginx | 要自己运维、扩缩容 |
| Serverless 函数 | 上传一个个函数（AWS Lambda 等） | 按调用计费、免运维 |
| **边缘函数（本项目）** | `functions/` 目录里每个文件就是一个接口 | **免运维 + 就近执行**（Cloudflare 全球节点） |

本项目用的是 **Cloudflare Pages Functions**：

- **前端**：`pnpm build` 产出的静态文件（`dist/`）由 Cloudflare CDN 伺服；
- **后端**：`functions/` 下每个 `.ts` 文件被自动变成**一个函数** —— **不用自己写路由注册**；
- **数据库**：**D1**（Cloudflare 的 SQLite 服务），代码里通过 `env.DB` 访问。

### 1.2 知识点：文件路径 = URL 路径（约定式路由）

| 文件 | 对应接口 |
|---|---|
| `functions/api/login.ts` | `POST /api/login` |
| `functions/api/me.ts` | `GET /api/me` · `PATCH /api/me` |
| `functions/api/puzzles/index.ts` | `GET /api/puzzles` · `POST /api/puzzles`（`index` 代表目录本身） |
| `functions/api/puzzles/[pid].ts` | `/api/puzzles/<任意 pid>`（**方括号 = 动态段**，值在 `params.pid`） |
| `functions/api/puzzles/[pid]/play.ts` | `POST /api/puzzles/<pid>/play` |
| `functions/api/puzzles/mine/[rowId].ts` | `GET /api/puzzles/mine/<rowId>` |
| `functions/_middleware.ts` | **特殊名**：所有请求都先经过它（§1.5） |

**本项目的全部接口一览**（权限 / 入参 / 出参一次列清）：

| 方法 | 路径 | 要登录 | 入参 | 出参（关键字段） |
|---|---|---|---|---|
| POST | `/api/register` | 否 | `{uname, password}` | `{token, user}` |
| POST | `/api/login` | 否 | `{uid, password}` | `{token, user}` |
| POST | `/api/logout` | 否（有 token 就删） | — | `204` 空响应 |
| GET | `/api/me` | **是** | — | `{user}` |
| PATCH | `/api/me` | **是** | `{uname}` | `{user}` |
| GET | `/api/puzzles` | 否（`?mine=1` 要） | 查询串 `limit/offset/mine/sort/uid/keyword` | `{items, total}` |
| POST | `/api/puzzles` | **是** | `{title, puzzleText, solutionText, visibility}` | 新题信息（`pid/rowId/...`） |
| GET | `/api/puzzles/:pid` | 否（private 要作者） | — | 题目详情（答案按 `show_solution`） |
| PATCH | `/api/puzzles/:pid` | **是（作者）** | 任意子集 `title/visibility/showSolution/puzzleText+solutionText` | `{ok:true}` |
| DELETE | `/api/puzzles/:pid` | **是（作者）** | — | `{ok:true}` |
| POST | `/api/puzzles/:pid/play` | **是** | — | `{playCount, counted}` |
| GET | `/api/puzzles/mine/:rowId` | **是** | — | 作者态全量详情 |

### 1.3 知识点：`wrangler.toml` 逐行（配置从哪来）

```toml
name = "sudoku-game"                    # 项目名（部署到 Cloudflare 时的名字）
pages_build_output_dir = "dist"         # 前端静态产物在哪 → wrangler pages dev 同时伺服 dist + functions
compatibility_date = "2026-10-11"       # Workers 运行时的"API 版本日期"（写死 → 行为稳定）

[[d1_databases]]                        # D1（SQLite）数据库绑定
binding = "DB"                          # ★ 代码里访问数据库的变量名：env.DB
database_name = "sudoku-db"             # 云端库名
database_id = "caeffb49-..."            # 云端库 id
```

**三个知识点**：

1. **`binding = "DB"` 必须与代码里的 `env.DB` 同名** —— 这就是 `functions/types.ts` 的来历：

```ts
/** Cloudflare 绑定（与 wrangler.toml 的 [[d1_databases]].binding 一致） */
export interface Env {
    DB: D1Database
}
```

2. **`compatibility_date` 是"运行时版本锁"**：Cloudflare 会持续调整运行时行为，写死日期保证"你的代码今天什么样，明年还什么样"；
3. **本地开发**：`npx wrangler pages dev` 同时起"静态服务器 + 本地 D1"，并把 `/api/*` 交给 `functions/`（前端 `vite.config.ts` 把 `/api` 代理到 `127.0.0.1:8788`）。

### 1.4 知识点：`PagesFunction` 与 `onRequest*`（一个接口就是一个导出函数）

```ts
export const onRequestPost: PagesFunction<Env> = async ({ request, env, params }) => { ... }
```

| 部分 | 含义 |
|---|---|
| `onRequestGet` / `Post` / `Patch` / `Delete` | **按 HTTP 方法分派**：想支持多种方法就导出多个（同一个文件内） |
| 参数对象 `{ request, env, params, next }` | `request`=请求；`env`=绑定（`env.DB`）；`params`=动态段（`params.pid`）；`next`=交给下一个处理者（中间件用） |
| `PagesFunction<Env>` | 泛型：告诉 TS "`env` 的类型是 `Env`" |
| 返回值 | 必须是 `Response`（`json()` / `fail()` / `new Response(null,{status:204})`） |

**本项目真实用法**：

```ts
// functions/api/me.ts —— 一个文件支持两种方法
export const onRequestGet: PagesFunction<Env> = async ({ request, env }) => { ... }     // 查我
export const onRequestPatch: PagesFunction<Env> = async ({ request, env }) => { ... }   // 改我
```
```ts
// functions/api/puzzles/[pid].ts —— 三种方法 + 动态参数
export const onRequestGet: ...    = async ({ request, env, params }) => { const row = await load(env, String(params.pid)); ... }
export const onRequestPatch: ...  = async ({ request, env, params }) => { ... }
export const onRequestDelete: ... = async ({ request, env, params }) => { ... }
```

**注意 `String(params.pid)`**：`params` 的值类型是 `string | string[] | undefined`，`String(...)` 把它收成 `string`（也顺手挡掉"同一层出现多个动态段"的边界情况）。

### 1.5 知识点：中间件 `_middleware.ts`（全局兜底）

```ts
import { fail } from './utils/json'
import type { Env } from './types'

/** 全局兜底：未捕获异常 → 统一 JSON（前端 client.ts 只解析 JSON） */
export const onRequest: PagesFunction<Env> = async (context) => {
    try {
        return await context.next()          // ① 交给真正的接口函数
    } catch (err) {
        const msg = err instanceof Error ? err.message : '服务器错误'
        return fail(msg, 500)                // ② 任何漏网异常都变成 JSON 500
    }
}
```

**为什么必须有它（逐行的意义）**：
- `_middleware.ts` 在"洋葱最外层"：所有请求先经过它，`context.next()` 才进到具体接口；
- 若某个接口里**抛了异常**（或数据库报错）没人接住，Cloudflare 默认会回 **HTML 错误页**；
- 而前端 `services/api/client.ts` **只会解析 JSON** → 拿到 HTML 就变成"未知错误"，用户看不懂；
- **所以后端必须保证"所有出口都是 JSON"** —— 这就是中间件存在的唯一理由（成功/参数错/未登录/异常四类出口都要一致）。

**通用知识点**：
> **跨层协议要保证"格式恒定"**：客户端按 JSON 解析，服务端就要在**每个出口**都产出 JSON。这就是"边界层兜底"的价值。

### 1.6 知识点：后端为什么能直接 import 前端的 `core/`

```ts
// functions/utils/puzzle.ts:1-5
import { EMPTY_GROUP_COPY } from '../../src/constants/game'
import { countBlanks } from '../../src/core/board/ops'
import { parsePuzzle } from '../../src/core/sudoku/parse'
import { getSudoku } from '../../src/core/sudoku/rules'
import { isBlankRatioOk } from '../../src/core/sudoku/shape'
```

**这是整个架构最值得记住的一点**：

- 前端（浏览器 / Worker）与后端（Cloudflare）**共用同一份 `src/core/**`**；
- 于是"题面格式、挖空比例、冲突判定"这些规则**只有一份实现**；**前端点提交时的即时校验**与**后端的服务端复校**跑的是**同一段代码**；
- 这也解释了 core 的两条铁律为什么必须存在（见 03 册）：
  1. **不碰平台 API 对象**（不用 `window` / `localStorage` / `fetch`）→ 否则后端 import 就炸；
  2. **不抛"业务异常"、用返回值表达失败**（00 册 §3.13）→ 后端里"用户输入不合法"是**正常业务**，应回 `400 + 原因`，而不是 `500`。

**为什么是相对路径而不是 `@/`**：`functions/tsconfig.json` 里**没有配 `paths`**（已核对），后端只能用 `../../src/...`（00 册 §2.5）。

## 2. HTTP 基础（看后端代码前必须有的概念）

### 2.1 知识点：一次请求由什么组成

```
POST /api/puzzles HTTP/1.1                     ← 方法 + 路径 + 协议版本
Host: example.com
Authorization: Bearer 3f9a...                  ← 头（headers）：元信息
Content-Type: application/json

{"title":"我的题","puzzleText":"0..."}          ← 体（body）：真正的数据
```

| 部分 | 含义 | 本项目例子 |
|---|---|---|
| **方法** | 想干什么（见 §2.2） | `GET` / `POST` / `PATCH` / `DELETE` |
| **路径** | 操作谁 | `/api/puzzles/Ab12Cd` |
| **查询串** | 过滤/分页（在 `?` 后） | `/api/puzzles?sort=hot&limit=10&offset=0` |
| **头** | 附加信息 | `Authorization: Bearer <token>`、`Content-Type` |
| **体** | 请求数据（JSON） | `{uname, password}` |

**后端代码怎么读它们**：

```ts
const url = new URL(request.url)                                   // 解析路径与查询串
url.searchParams.get('limit')                                      // 读查询参数
request.headers.get('Authorization')                               // 读头
await request.json<Payload>()                                      // 读体（并指定类型）
```

### 2.2 知识点：四个方法各自的语义（本项目完全遵守）

| 方法 | 语义 | 幂等？ | 本项目用途 |
|---|---|---|---|
| `GET` | **读**，不改数据 | ✅ 是 | 取列表、取详情、取我 |
| `POST` | **创建**（或触发动作） | ❌ 否（调两次建两条） | 注册、登录、新建题、计数（play）、登出 |
| `PATCH` | **部分修改**（只改给的字段） | 一般 ✅ | 改标题/可见性/答案、改我的显示名 |
| `DELETE` | **删除** | ✅ 是 | 删题 |

**为什么用 `PATCH` 而不是 `PUT`**：`PUT` 语义是"**整份替换**"（没给的字段会被清空）；本项目后端就是"**只处理你在 body 里出现的字段**"（看 `[pid].ts` 里那一串 `if (body.xxx !== undefined)`），所以 `PATCH` 才是正确语义。

### 2.3 知识点：状态码（本项目出现的每一个）

| 码 | 含义 | 本项目哪里 |
|---|---|---|
| `200` | 成功（带 JSON 体） | 绝大多数接口 |
| `204` | 成功但**没有响应体** | `logout.ts` → `new Response(null, { status: 204 })` |
| `400` | 请求有问题（参数/格式） | `fail('标题必填')`、`AUTH_COPY.badPayload` |
| `401` | **没登录 / 登录过期** | `requireUser` 返回的 `fail(AUTH_COPY.needAuth, 401)` |
| `404` | 不存在**或无权访问** | 题目 private 且不是作者 → 也回 404（**不暴露"这题存在"**） |
| `429` | 请求太频繁（限流） | 登录失败过多：`fail('尝试次数过多，请 N 分钟后再试', 429)` |
| `500` | 服务器自己出错了 | `_middleware.ts` 兜底 |

**两个安全细节**：
- **404 与 401 的区别**："没登录"回 401（前端能据此弹登录）；"**别人的私密题**"回 **404**（不泄露存在性）；
- **429 的文案由后端独有**（注释写明"后端专属文案，前端不会出现同句"），因为只有后端知道还剩几分钟。

### 2.4 知识点：JSON 的两种固定形状（本项目约定）

```ts
// functions/utils/json.ts（全文 9 行）
/** 统一 JSON 响应 */
export const json = (data: unknown, status = 200): Response =>
    new Response(JSON.stringify(data), {
        status,
        headers: { 'content-type': 'application/json; charset=utf-8' },
    })

/** 统一错误响应（前端 client.ts 会把 error 字段提出来当 Error.message） */
export const fail = (error: string, status = 400): Response => json({ error }, status)
```

**约定**：
- **成功** = `{ ...业务字段 }`（如 `{token, user}`、`{items, total}`）；
- **失败** = `{ error: '人类可读的原因' }`（前端会**直接把它显示出来**）；
- 因此**后端的错误文案要写成"用户能看懂的中文"**（例如"挖空比例需在 40%~65% 之间（当前 30%）"），而不是"ERR_INVALID_RATIO"。

**为什么默认 `status = 400`**：`fail()` 的绝大多数调用都是"参数不对"，默认值让调用处更短（只有 401/404/429/500 才传第二个参数）。

## 3. SQL 与 D1（数据库这一层）

### 3.1 知识点：关系型数据库的最小概念集

| 概念 | 一句话 | 本项目实例 |
|---|---|---|
| **表（table）** | 二维表：行 = 记录，列 = 字段 | `user`、`session`、`puzzle` |
| **主键（PRIMARY KEY）** | 唯一标识一行的列（自动唯一 + 有索引） | `user.uid`、`session.token`、`puzzle.pid` |
| **唯一约束（UNIQUE）** | 该列不许重复 | `puzzle.row_id` |
| **索引（INDEX）** | 加速"按某列查/排序" | `idx_puzzle_hot` |
| **外键（FOREIGN KEY）** | 表之间的引用约束 | **本项目不建**（见下） |
| **时间戳** | 存"毫秒数"整数而不是日期字符串 | `created_at INTEGER`、`Date.now()` |

**为什么本项目不建外键**：Serverless/D1 场景下，一致性由**应用层逻辑**保证（删题时**手工** `DELETE FROM puzzle_play`，见 `[pid].ts` 的 `batch`）——少一层约束就少一次额外检查与迁移麻烦。**这是权衡，不是疏忽。**

**为什么时间存整数**：比较/排序/算差值都直接用数字（`s.expires_at > ?` 传 `Date.now()`），无需时区与格式转换。

### 3.2 知识点：`schema.sql` 逐表精读（5 张表 + 3 个索引）

```sql
CREATE TABLE IF NOT EXISTS user (          -- 用户
  uid TEXT PRIMARY KEY,                    -- 账号 ID（登录用的是它）
  uname TEXT NOT NULL,                     -- 显示名（允许重名）
  password_hash TEXT NOT NULL,             -- 口令哈希（永不存明文）
  salt TEXT NOT NULL,                      -- 每用户独立盐
  created_at INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS session (       -- 会话（登录凭据）
  token TEXT PRIMARY KEY,                  -- 随机 32 字节 hex
  uid TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  expires_at INTEGER NOT NULL              -- 过期时间（毫秒）
);

CREATE TABLE IF NOT EXISTS login_attempt ( -- 登录限流
  uid TEXT PRIMARY KEY,
  fails INTEGER NOT NULL DEFAULT 0,        -- 连错次数
  locked_until INTEGER NOT NULL DEFAULT 0, -- 锁到什么时候（0 = 没锁）
  last_at INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS puzzle (        -- 题目
  pid TEXT PRIMARY KEY,                    -- 公开分享用
  row_id TEXT NOT NULL UNIQUE,             -- 作者视角的行标识
  uid TEXT NOT NULL,                       -- 作者
  title TEXT NOT NULL,
  puzzle TEXT NOT NULL,                    -- 题面串（0 = 空）
  solution TEXT NOT NULL,                  -- 答案串
  side_s INTEGER NOT NULL,                 -- 边长 S（冗余存）
  blank_count INTEGER NOT NULL,            -- 挖空数（冗余存）
  visibility TEXT NOT NULL DEFAULT 'public',
  show_solution INTEGER NOT NULL DEFAULT 0,-- 是否公开答案（0/1）
  play_count INTEGER NOT NULL DEFAULT 0,   -- 热度
  created_at INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS puzzle_play (   -- 谁玩过（热度去重用）
  pid TEXT NOT NULL,
  uid TEXT NOT NULL,
  played_at INTEGER NOT NULL,
  PRIMARY KEY (pid, uid)                   -- ★ 复合主键：同人同题只有一行
);
```

**要看出四个设计点**：

1. **`pid`（公开）与 `row_id`（作者行标识）是两个 ID**：分享/挑战走 `pid`（`/api/puzzles/:pid`），"我的题目"列表走 `row_id`（`/api/puzzles/mine/:rowId`），**列表里不暴露 pid**；
2. **`side_s` / `blank_count` 是"冗余字段"**（本可由串算出来）—— **有意的性能权衡**：列表页只显示"9×9 · 挖空 45"，若每次都要解析几万字的题面串才能显示，代价太高。
   > 这与"派生数据不进 store"（01 册 §2.4）不矛盾：那条讲**内存中的响应式状态**；这里的冗余是为了**避免把大字段读出来**，属于存储层的反范式化。
3. **`show_solution` 用 0/1 而不是布尔** —— SQLite 没有布尔类型；
4. **`puzzle_play` 的复合主键 `(pid, uid)`** —— 天然保证"同人同题只有一条"，配合后面的 `ON CONFLICT` 刷新时间。

**三个索引为什么这么建**：

```sql
CREATE INDEX idx_puzzle_public ON puzzle(visibility, created_at DESC);                  -- 「最新」
CREATE INDEX idx_puzzle_hot    ON puzzle(visibility, play_count DESC, created_at DESC);  -- 「最热」
CREATE INDEX idx_puzzle_uid    ON puzzle(uid, created_at DESC);                         -- 「我的题目」
```

规则：**第一列放"过滤/分组"的列**（`visibility` / `uid`），**后面跟"排序"的列** → "过滤 + 排序"能在索引里一次走完，不必全表扫描再排序。
这正是 `puzzles/index.ts` 那三条查询（公开最新 / 公开最热 / 我的）能快的原因。

### 3.3 知识点：D1 的四个 API（本项目用到的全部）

```ts
env.DB.prepare('SELECT ... WHERE uid = ?')     // ① 准备一条 SQL（? 是占位符）
      .bind(me.uid)                            // ② 绑定参数（防注入 + 类型清晰）
      .first<{ n: number }>()                  // ③ 取第一行（无则 null）
      .all()                                   // ③ 取多行 → { results: [...] }
      .run()                                   // ③ 只执行（不关心行）
env.DB.batch([stmt1, stmt2])                    // ④ 批量执行（一个整体）
```

**真实对照（全部来自本项目）**：

```ts
// first：查总数（puzzles/index.ts:18-19）
const counted = await env.DB.prepare('SELECT COUNT(*) AS n FROM puzzle WHERE uid = ?')
    .bind(me.uid).first<{ n: number }>()
const total = counted?.n ?? 0                    // ← 可能为 null → ?? 兜底

// all：查列表（puzzles/index.ts:20-25）
const { results } = await env.DB.prepare(
    `SELECT row_id AS rowId, title, side_s AS sideS, ... LIMIT ? OFFSET ?`,
).bind(me.uid, limit, offset).all()

// run：写入（register.ts:26-28）
await env.DB.prepare('INSERT INTO user (uid, uname, password_hash, salt, created_at) VALUES (?,?,?,?,?)')
    .bind(uid, uname, await hashPassword(password, salt), salt, now).run()

// batch：两件事一起做（[pid].ts:84-87）
await env.DB.batch([
    env.DB.prepare('DELETE FROM puzzle_play WHERE pid = ?').bind(pid),
    env.DB.prepare('DELETE FROM puzzle WHERE pid = ?').bind(pid),
])
```

**`batch` 的意义**：多条语句**作为一个整体**执行 —— 要么都成功、要么都不生效。删题时"先删游玩记录再删题"，只成功一半就会留下孤儿数据。

**`AS rowId` 是列别名**：数据库列名是蛇形（`row_id`），前端要驼峰（`rowId`）→ **在 SQL 里改名**，前端就不必再做一遍转换（本项目统一在 SQL 层完成"命名转换"）。

### 3.4 知识点：SQL 注入与"参数化查询"（安全第一课）

**反例（绝对禁止）**：

```ts
const sql = `SELECT * FROM user WHERE uid = '${uid}'`      // ❌ 注入漏洞
```

攻击者传 `uid = "' OR '1'='1"` → 语句变成 `WHERE uid = '' OR '1'='1'` → **查出所有人**；传 `"'; DROP TABLE user; --"` → **删表**。

**正确做法（本项目全部这么写）**：

```ts
const sql = 'SELECT uid, uname FROM user WHERE uid = ?'    // ✅ 占位符
await env.DB.prepare(sql).bind(uid).first()                //    参数单独传
```

**原理**：SQL 的**结构**先被编译好，参数只作为**值**填进去，**永远无法改变结构**。

**本项目的"排序白名单"（经典细节）**：

```ts
// puzzles/index.ts:29-32
// ORDER BY 只来自白名单，绝不拼用户输入
const order = url.searchParams.get('sort') === 'hot'
    ? 'p.play_count DESC, p.created_at DESC'
    : 'p.created_at DESC'
```

**为什么排序要特殊处理**：`ORDER BY ?` 在 SQL 里**不合法**（列名不能用参数替代），"按什么排序"只能拼字符串 → 所以必须**白名单**（只认 `hot`，其它一律默认），**绝不能**把用户输入直接拼进 `ORDER BY`（那一样可注入）。

**模糊搜索的写法**：

```ts
const keyword = (url.searchParams.get('keyword') ?? '').trim()
const like = `%${keyword}%`                                  // LIKE 的通配符自己加
// ... AND (? = '' OR p.title LIKE ? OR u.uname LIKE ?)       空关键字时整段条件恒真
```
注意 `like` 是**作为值绑进去的**（`bind(..., like, like)`），`%` 只是 LIKE 的通配符，**与注入无关**。

### 3.5 知识点：`ON CONFLICT ... DO UPDATE`（"有则更新、无则插入" = upsert）

**场景一：登录失败计数（`login.ts:32-37`）**

```sql
INSERT INTO login_attempt (uid, fails, locked_until, last_at) VALUES (?,?,?,?)
ON CONFLICT(uid) DO UPDATE SET fails = excluded.fails,
                               locked_until = excluded.locked_until,
                               last_at = excluded.last_at
```

- `ON CONFLICT(uid)`：**主键冲突**时（该 uid 已有记录）走 `DO UPDATE`；
- `excluded.xxx`：SQLite 关键字，指"**本次本来要插入的那一行**"的值。

**场景二：游玩记录（`[pid]/play.ts:24-27`）**

```sql
INSERT INTO puzzle_play (pid, uid, played_at) VALUES (?,?,?)
ON CONFLICT(pid, uid) DO UPDATE SET played_at = excluded.played_at
```

**作用**：同一个人重复玩同一题**不会插出第二行**，只刷新时间 → 于是"热度去重"的判据（查这行的时间）永远成立。

**为什么不用"先查再改"**：`查 → 判断 → 写` 之间可能被并发插入打断；**一条 upsert 是原子的**。

### 3.6 知识点：分页（`LIMIT / OFFSET` + `total`）

```ts
// puzzles/index.ts:11-12（读参数并夹紧范围）
const limit = Math.min(Number(url.searchParams.get('limit') ?? 10) || 10, 50)
const offset = Math.max(Number(url.searchParams.get('offset') ?? 0) || 0, 0)
```

**三个防御性写法**：
1. **`Number(用户输入)`**：转数字（`Number('abc')` → `NaN`）；
2. **`|| 默认值`**：`NaN` 是假值 → 回落到 `10` / `0`；
3. **`Math.min(..., 50)` / `Math.max(..., 0)`**：**夹紧范围** —— 否则用户传 `limit=999999` 就是"一次拉全库"（DoS 隐患）。

**为什么要 `total`**：前端分页组件要知道"一共几页"。所以列表接口都跑**两条查询**：`COUNT(*)` + 数据（本项目就是这么做的，`puzzles/index.ts:41-52`）。

**性能补充**：大偏移量（`OFFSET 10000`）会越翻越慢（数据库必须跳过前面的行）。本项目规模用 `OFFSET` 完全够；数据量再大就要换**游标分页**（`WHERE created_at < 上一页最后一条的时间`）。

## 4. 认证与安全（本项目最"硬"的一段代码）

> 这一节的代码全在 `functions/utils/auth.ts`（60 行）与 `functions/utils/id.ts`（34 行）里 —— **短，但每个字符都有原因**。

### 4.1 知识点：密码存储的三条铁律

**铁律一：绝不存明文，也不能"可逆加密"。**

| 做法 | 能不能用 | 原因 |
|---|---|---|
| 明文存储 | ❌ | 库被拖 → 所有用户密码泄露（用户往往到处用同一密码） |
| 可逆加密（AES 等） | ❌ | 密钥泄露 = 全泄露；且系统里**没有任何地方需要还原原密码** |
| **单向哈希**（本项目） | ✅ | 只做"验证一致性"：拿输入重新算一遍对比 |

**铁律二：必须加盐（salt）—— 每个用户一个随机盐。**

```ts
// 不用盐：hash('123456') 对所有人都是同一个值
// 攻击者预先算好"常见密码 → 哈希"的表（彩虹表），一撞就中
// 用盐：hash('123456' + 'a1b2c3...')  每个用户的哈希都不同 → 彩虹表失效
```

**铁律三：必须用"慢哈希"（迭代哈希）。**

普通哈希（如 SHA-256）快得可怕 —— 显卡一秒能算几十亿次，暴力破解很快。
**PBKDF2** 就是"**故意算得慢**"的算法：它把哈希**迭代很多次**（本项目 `AUTH_ITERATIONS = 10_000`），让单次验证耗时毫秒级：

- 对正常用户：登录慢 10ms，**完全无感**；
- 对暴力破解者：**每试一个密码都要付同样的代价** → 破解成本乘以 10000 倍。

> 本项目注释写着"Workers CPU 限额内；必要时下调" —— **这是"安全强度"与"边缘运行时 CPU 预算"之间的取舍**，是个很真实的工程判断。

### 4.2 知识点：`auth.ts` 逐段精读（60 行，全部）

**① 常量（四个参数决定安全策略）**

```ts
/** PBKDF2 迭代（Workers CPU 限额内；必要时下调） */
export const AUTH_ITERATIONS = 10_000
/** 会话有效期：7 天 */
export const SESSION_TTL = 7 * 24 * 3600_000        // 7 天毫秒数（可读的写法：7*24*3600*1000）
/** 登录限流：连续失败 5 次锁 10 分钟 */
export const MAX_FAILS = 5
export const LOCK_MS = 10 * 60_000                  // 数字分隔符 _ 只是给人看的：10 分钟
```

**② 字节 → 十六进制字符串**

```ts
const toHex = (bytes: Uint8Array): string =>
    [...bytes].map(b => b.toString(16).padStart(2, '0')).join('')
```

逐点解释：

- `bytes` 是 `Uint8Array`（00 册 §3.10），**不能直接 `.map`**（它不是真数组）→ `[...bytes]` 先摊成普通数组；
- `b.toString(16)`：把 0~255 转成十六进制（如 `15` → `'f'`）；
- **`padStart(2, '0')`**：不满 2 位前面补 0（`'f'` → `'0f'`）—— **这一步不能省**，否则 `0x0f` 会变成 1 个字符，整串长度不固定，比对必然出错；
- `.join('')`：拼成一个长字符串（如 `'a3f9...'`）。

**为什么要转 hex 而不是存二进制**：数据库 `TEXT` 字段好存、日志里可打印、调试时肉眼可看。

**③ 盐与 token 的生成**

```ts
/** 16 字节盐（hex） */
export const makeSalt = (): string => toHex(crypto.getRandomValues(new Uint8Array(16)))
/** 32 字节会话 token（hex） */
export const makeToken = (): string => toHex(crypto.getRandomValues(new Uint8Array(32)))
```

**为什么必须用 `crypto.getRandomValues` 而不是 `Math.random`**：

- `Math.random()` 是**伪随机**（内部状态可被推测），**不是密码学安全**的；用它生成 token = 别人可以预测出别人的 token；
- `crypto.getRandomValues` 来自操作系统的密码学随机源，**不可预测**；
- 熵：16 字节 = 128 bit；32 字节 = 256 bit（暴力猜 token 不现实）。

**④ 口令哈希（PBKDF2-SHA256）**

```ts
export const hashPassword = async (password: string, salt: string): Promise<string> => {
    const enc = new TextEncoder()
    const key = await crypto.subtle.importKey('raw', enc.encode(password), 'PBKDF2', false, ['deriveBits'])
    const bits = await crypto.subtle.deriveBits(
        { name: 'PBKDF2', salt: enc.encode(salt), iterations: AUTH_ITERATIONS, hash: 'SHA-256' },
        key,
        256,
    )
    return toHex(new Uint8Array(bits))
}
```

**逐行**：

1. `new TextEncoder()` + `enc.encode(x)`：**把字符串变成 UTF-8 字节**（Web Crypto API 只认字节，不认字符串）；
2. `importKey('raw', 密码字节, 'PBKDF2', false, ['deriveBits'])`：把"原始密码"包装成一把只**允许派生**的密钥对象（`false` = 不可导出，防止被读回）；
3. `deriveBits({name:'PBKDF2', salt, iterations, hash:'SHA-256'}, key, 256)`：**跑 10000 轮**，产出 256 bit（32 字节）；
4. `toHex(new Uint8Array(bits))`：转成 hex 存进 `user.password_hash`。

**注意**：`salt` 在本项目是**十六进制字符串**，这里直接 `enc.encode(salt)` 当"盐文本"用 —— 只要"存的和算的用的是同一个字符串"就正确（一致性比形式重要）。
**验证流程**：登录时拿**库里存的 salt** 重算一遍，与**库里存的 hash** 比对（`login.ts:46`）。

### 4.3 知识点：恒定时间比较（防"时序侧信道"）

```ts
/** 恒定时间比较（避免时序侧信道） */
export const safeEqual = (a: string, b: string): boolean => {
    if (a.length !== b.length) return false
    let diff = 0
    for (let i = 0; i < a.length; i++) diff |= a.charCodeAt(i) ^ b.charCodeAt(i)
    return diff === 0
}
```

**为什么不能直接 `a === b`**：
字符串比较是**从前往后逐字符比**，发现不同就**立刻返回 false**。于是"前 3 位对"和"一位都不对"的耗时**不同**。
攻击者可以：
- 不断尝试、**测量响应时间**，一位一位地把正确哈希"猜"出来（这叫**时序攻击 timing attack**）；
- 哈希是 hex 字符串、内容固定长度，非常适合这种攻击。

**这段代码怎么防**：

| 写法 | 作用 |
|---|---|
| `diff \|= a.charCodeAt(i) ^ b.charCodeAt(i)` | `^`（异或）：**相同为 0、不同为非 0**；`\|=` 把它**累积**到 `diff`（**不提前退出**，走完全部字符） |
| 最后才 `diff === 0` | 只有**全部字符都相同**，累积结果才是 0 |
| `if (a.length !== b.length) return false` | 长度不同直接返回（长度本身不是秘密，因为它固定为 64 个 hex 字符） |

**通用知识点（一定要带走）**：
> **凡是"秘密值的比较"（token、哈希、签名），都不要用 `===`，要用恒定时间比较。** 因为"快慢"本身就是信息。

**⑤ `requireUser`（"要登录"的唯一入口）**

```ts
export const requireUser = async (
    request: Request,
    env: Env,
): Promise<{ uid: string; uname: string } | Response> => {
    const token = request.headers.get('Authorization')?.replace(/^Bearer\s+/i, '')
    if (!token) return fail(AUTH_COPY.needAuth, 401)            // ① 没带头 → 401「请先登录」

    const row = await env.DB.prepare(
        'SELECT u.uid AS uid, u.uname AS uname FROM session s JOIN user u ON u.uid = s.uid \
         WHERE s.token = ? AND s.expires_at > ?',
    )
        .bind(token, Date.now())
        .first<{ uid: string; uname: string }>()

    if (!row) return fail(AUTH_COPY.sessionExpired, 401)        // ② token 无效/过期 → 401
    return row                                                   // ③ 成功 → 返回用户
}
```

**逐行 + 四个知识点**：

1. **`Authorization: Bearer <token>` 的解析**：`?.replace(/^Bearer\s+/i, '')` —— 正则去掉开头的 `Bearer `（`i` = 忽略大小写，`\s+` = 至少一个空白）。**`?.` 是防"没有这个头"**（`get` 返回 `null`）。
2. **一条 SQL 同时校验 token 与过期时间**（`s.expires_at > ?` 传 `Date.now()`）—— **过期判断放在查询里**，不需要"先查出来再在 JS 里比时间"。
3. **返回类型 `{uid,uname} | Response` 是这份代码的一个巧妙设计**：
   - 成功 → 返回用户数据；失败 → 返回一个**已经可以发出去的 Response**；
   - 于是调用方只需写三行：

```ts
const me = await requireUser(request, env)
if (me instanceof Response) return me       // ← 失败直接发出去，成功继续
```
4. **为什么用 `instanceof Response` 而不是别的判别方式**：`Response` 是**运行期真实存在的类**（不是 TS 的纯类型），`instanceof` 在运行时能可靠区分"这是响应对象还是用户数据"。这比"返回 `{ok:false}` 再层层判断"更省代码 —— 属于"**用类型系统 + 运行时断言共同表达二选一**"的实战技巧。

**顺带理解一个设计取舍**：本项目**没有"定时清理过期 session"的任务**（`session` 表里过期行会留着），因为：
- **正确性不依赖删除**（查询条件已经过滤掉过期的）；
- Serverless 环境没有常驻进程，加"定时任务"反而复杂；
- `logout` 只删**当前 token** 那一行（`logout.ts:5`）—— 够用。
这是"**读时过滤 vs 写时清理**"的取舍，不是遗漏。

### 4.4 知识点：登录限流（防暴力破解）逐段（`login.ts:18-49`）

**为什么要限流**：如果密码可以无限次快速尝试，那么"短密码 + 常见密码"很快就被撞开。**限流把"无限次尝试"变成"每 10 分钟只能试 5 次"。**

```ts
const now = Date.now()
const attempt = await env.DB.prepare('SELECT fails, locked_until FROM login_attempt WHERE uid = ?')
    .bind(uid).first<{ fails: number; locked_until: number }>()

// ① 还在锁定期内 → 直接 429，并告诉还剩几分钟
if (attempt && attempt.locked_until > now) {
    const mins = Math.ceil((attempt.locked_until - now) / MIN_MS)     // MIN_MS = 60_000
    return fail(`尝试次数过多，请 ${mins} 分钟后再试`, 429)
}

/** ② 记一次失败（到阈值就锁定 10 分钟） */
const recordFail = async (): Promise<Response> => {
    const fails = (attempt?.fails ?? 0) + 1
    const locked = fails >= MAX_FAILS ? now + LOCK_MS : 0
    await env.DB.prepare(
        `INSERT INTO login_attempt (uid, fails, locked_until, last_at) VALUES (?,?,?,?)
         ON CONFLICT(uid) DO UPDATE SET fails = excluded.fails, ...`,
    ).bind(uid, locked ? 0 : fails, locked, now).run()      // ★ 见下面的解释
    return fail(AUTH_COPY.badCredentials, 401)
}
```

**四个必须看懂的细节**：

| # | 细节 | 为什么 |
|---|---|---|
| ① | `Math.ceil((locked_until - now) / 60_000)` | 剩余时间要**向上取整**：还剩 30 秒也应提示"1 分钟"，不能显示"0 分钟"（用户会以为可以马上试） |
| ② | **`locked ? 0 : fails`** | **锁定的那一刻把计数归零** —— 因为此后判据变成 `locked_until`，如果再累加 `fails`，解锁后第一次失败就会立刻又被锁（体验极差） |
| ③ | **`if (!user) return recordFail()`** | **用户不存在也照样累加失败** —— 否则"是否被限流"会暴露"账号是否存在"（**账号枚举攻击**） |
| ④ | 失败统一回 `AUTH_COPY.badCredentials`（"账号 ID 或密码错误"） | **不区分**"账号不存在"与"密码错误" → 攻击者无法据此判断账号是否存在 |

**登录成功后要清计数（`login.ts:49`）**：

```ts
await env.DB.prepare('DELETE FROM login_attempt WHERE uid = ?').bind(uid).run()
```
**为什么必须清**：否则"历史失败次数"会一直累积，用户偶尔打错几次、几个月后又被锁。

**通用知识点（三条防攻击套路，本项目全用了）**：
1. **限流/退避**（429 + 锁定期）—— 让"暴力尝试"变慢；
2. **消息不泄露信息**（统一错误文案）—— 让攻击者**问不出**有价值的信息；
3. **对所有分支一视同仁**（不存在用户也走同样的失败路径与耗时逻辑）—— 避免**时序/行为**泄漏。

### 4.5 知识点：`id.ts` 逐段（"为什么 ID 不用 UUID"）

```ts
const BASE62 = 'ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789'
/** rowId 长度（后端专属：前端只透传，不校验） */
const ROW_ID_LENGTH = 8

/** 生成 len 位 base62 随机串（拒绝采样，无取模偏差；用 crypto 不用 Math.random） */
export const makeId = (len: number): string => {
    const out: string[] = []
    while (out.length < len) {
        for (const b of crypto.getRandomValues(new Uint8Array(len))) {
            if (b < 248) out.push(BASE62[b % 62])      // 248 = 62×4 → 丢 8 个值，保证均匀
            if (out.length === len) break
        }
    }
    return out.join('')
}

export const makeUid = (): string => makeId(UID_LENGTH)       // 用户 uid（20 位）
export const makePid = (): string => makeId(UID_LENGTH)       // 题目 pid（20 位）
export const makeRowId = (): string => makeId(ROW_ID_LENGTH)  // 我的题目行标识（8 位）
```

**① 为什么用 base62（A-Z a-z 0-9）而不是 hex**：
hex 只有 16 个字符（每字符 4 bit），base62 有 62 个（每字符 ≈ 5.95 bit）→ **同样长度能带更多熵**，或**同样熵可以更短**。

**算一下安全余量**：
- `uid`/`pid`：20 位 × log₂62 ≈ **119 bit** → 碰撞概率低到可以忽略（生日界约 2⁶⁰ 量级才需要考虑）；
- `rowId`：8 位 ≈ **47.6 bit**（≈ 2.2×10¹⁴）→ 对"私人入口标识"足够，且**它还有 `UNIQUE` 约束 + 查重重试**兜底。

**② 为什么要"拒绝采样"（`if (b < 248)`）——这是本节最值得学的一点**：

- 一个随机字节是 0~255（256 个值），而 base62 只有 62 个字符；
- 天真做法：`BASE62[b % 62]` —— 但 **256 不是 62 的整数倍**（62×4 = 248，余 8）：
  - `b = 0..247` 时，每个下标被映射到的字节数都是 4 个（均匀）；
  - `b = 248..255` 时会**额外**多出 8 个字节映射到 `BASE62[0..7]` → **前 8 个字符出现概率偏高**；
- **拒绝采样**：`b ≥ 248` 直接丢掉（不产出字符），只用 0~247 → **每个字符严格等概率**。

**通用知识点**：
> **"取模映射到非整除范围"一定有偏置**；要么**拒绝采样**丢多余值，要么用"更大范围再取模"。这在抽卡概率、随机分布、哈希分桶里都是同一个坑。

**③ 为什么 `while (out.length < len)` 外面还要套循环**：
一次 `getRandomValues(len)` 只有 `len` 个字节，丢掉一些后（≈3% 被丢）**不够 len 个**，所以要继续取直到凑够 —— `while` 就是干这个的。

**④ 为什么不直接用 UUID**：
- UUID 太长（36 字符含横线），**用户要手抄/口述/复制**（本项目 uid 是登录凭据，UI 里有"复制"按钮、还提示"请保存到安全的地方"）；
- 20 位 base62 更短、无横线，且熵足够。

**⑤ `makeUniqueId`（查重 + 重试）**

```ts
export const makeUniqueId = async (
    gen: () => string,
    exists: (id: string) => Promise<boolean>,
    tries = 5,
): Promise<string> => {
    for (let i = 0; i < tries; i++) {
        const id = gen()
        if (!(await exists(id))) return id
    }
    throw new Error('id 生成冲突，请重试')
}
```

**知识点**：
- **高阶函数**：参数是"生成函数"和"判存函数" → 同一段逻辑服务 uid / pid / rowId 三种 ID（`register.ts:20`、`puzzles/index.ts:79-82`）；
- **为什么要查重**：虽然 119 bit 几乎不可能撞，但**数据库有 `PRIMARY KEY`/`UNIQUE`**，一旦撞了就会 500；先查一次成本很低，把"不可能"变成"绝不"；
- **抛异常在这里是合理的**（对比 core 的"不抛"）：这是**基础设施层的兜底**（连续 5 次都撞 = 系统性问题），不是业务分支。**同一个项目里不同层次的错误策略可以不同，关键是要清醒。**

### 4.6 知识点：字段收口 `toPublicUser`

```ts
// functions/utils/user.ts（全文 3 行）
import type { User } from '../../src/types/user'

/** 对外暴露的用户字段（收口在此：不泄露 password_hash / salt） */
export const toPublicUser = (uid: string, uname: string): User => ({ uid, uname, isGuest: false })
```

**为什么要有这么一个"看起来多余"的函数**：

- 数据库里的行有 `password_hash` / `salt` —— **绝不能让它们出现在任何响应里**；
- 如果每个接口各自手写 `{ uid, uname, isGuest: false }`，早晚有人写成 `{...row}` 或漏删字段；
- **收口到一个函数**后：① 只要不通过它，就发不出去；② 以后加字段（如头像）只改一处。

**通用知识点（非常重要）**：
> **"出站数据"要经过一个显式的转换层**（`toXxxDto` / `toPublicXxx`），**永远不要把数据库行直接 `JSON.stringify` 出去**。这是防"意外泄露敏感字段"的最简单也最有效的手段。
> 本项目在 `[pid].ts` 里也是**手写字段列表**（而不是 `json(row)`），同一思想。

### 5.0 知识点：每个接口都是同一套"五步"

```ts
export const onRequestXxx: PagesFunction<Env> = async ({ request, env, params }) => {
    // ① 解析入参：读 body / query / params（永远假设"用户会乱传"）
    // ② 校验：格式、长度、取值白名单 → 不对就 return fail(...)
    // ③ 鉴权：需要登录就先 const me = await requireUser(...); if (me instanceof Response) return me
    // ④ 查/写库：参数化查询（+ 必要时 batch）
    // ⑤ 出站：手写字段列表 + json()（绝不直接吐数据库行）

```

**为什么强调这个套路**：你以后要加一个接口（比如"收藏题目"），照着五步抄，**不会漏鉴权、不会漏校验、不会泄露字段**。

### 5.1 精读 `register.ts`（36 行，全文）

```ts
import { AUTH_COPY, PASSWORD_MIN, UNAME_PATTERN } from '../../src/constants/user'
import { hashPassword, makeSalt, makeToken, SESSION_TTL } from '../utils/auth'
import { makeUid, makeUniqueId } from '../utils/id'
import { fail, json } from '../utils/json'
import { toPublicUser } from '../utils/user'
import type { Env } from '../types'

interface Payload { uname?: string; password?: string }

export const onRequestPost: PagesFunction<Env> = async ({ request, env }) => {
    let body: Payload
    try { body = await request.json<Payload>() } catch { return fail(AUTH_COPY.badPayload) }   // ①

    const uname = (body.uname ?? '').trim()                                                    // ②
    const password = body.password ?? ''
    if (!UNAME_PATTERN.test(uname)) return fail(AUTH_COPY.unameInvalid)                        // ③
    if (password.length < PASSWORD_MIN) return fail(AUTH_COPY.passwordTooShort)

    // uid：生成 + 查重
    const uid = await makeUniqueId(makeUid, async id =>
        !!(await env.DB.prepare('SELECT 1 FROM user WHERE uid = ?').bind(id).first()),
    )                                                                                          // ④

    const salt = makeSalt()
    const now = Date.now()
    await env.DB.prepare(
        'INSERT INTO user (uid, uname, password_hash, salt, created_at) VALUES (?,?,?,?,?)',
    ).bind(uid, uname, await hashPassword(password, salt), salt, now).run()                     // ⑤

    const token = makeToken()
    await env.DB.prepare(
        'INSERT INTO session (token, uid, created_at, expires_at) VALUES (?,?,?,?)',
    ).bind(token, uid, now, now + SESSION_TTL).run()                                            // ⑥

    return json({ token, user: toPublicUser(uid, uname) })                                      // ⑦
}
```

**逐点解释**：

| # | 代码 | 知识点 |
|---|---|---|
| ① | `try { await request.json<Payload>() } catch { return fail(...) }` | **请求体不是合法 JSON 时 `request.json()` 会抛异常** —— 必须接住并回 400；`<Payload>` 是泛型断言"我期望这个形状"（字段仍可能缺 → 所以类型写成 `uname?`） |
| ② | `(body.uname ?? '').trim()` | **三层防御**：可能没传（`?? ''`）、可能带空格（`trim()`）、可能不是字符串（`''.trim()` 保证后续 `test` 拿到字符串） |
| ③ | `UNAME_PATTERN.test(uname)` | **正则校验集中在前端/后端共用的常量**（`src/constants/user.ts`）→ 前端即时校验、后端复校**用同一个来源**（`UNAME_PATTERN = /^[\w\u4e00-\u9fa5]{2,16}$/`） |
| ④ | `makeUniqueId(makeUid, async id => !!(await ...first()))` | **`!!`** 把"有值/`undefined`"变成 `true`/`false`（`first()` 返回行对象或 `null`）；`SELECT 1` 只查"存不存在"，不取数据 |
| ⑤ | 密码**先哈希再加盐**入库 | 库里永远没有明文；`await hashPassword(...)` 是**慢操作**（10000 轮），所以整个接口会慢几毫秒 —— 正常 |
| ⑥ | 注册成功**直接建会话** | 用户不用"注册完再登录一次"（体验）；`expires_at = now + SESSION_TTL` |
| ⑦ | `json({ token, user: toPublicUser(uid, uname) })` | **一次返回 token + 用户资料**：前端拿到就能立刻进入登录态（`stores/user.ts` 的 `register`） |

**这里有个值得注意的"顺序"**：**先校验 → 再生成 uid → 再哈希 → 再写库**。慢操作（哈希）**放在所有"能提前失败"的检查之后**，避免"参数不合法却先算了一次哈希"的浪费。

### 5.2 精读 `login.ts`（56 行，限流部分已在 §4.4 讲过，这里看剩余部分）

```ts
interface Payload { uid?: string; password?: string }
const MIN_MS = 60_000

export const onRequestPost: PagesFunction<Env> = async ({ request, env }) => {
    let body: Payload
    try { body = await request.json<Payload>() } catch { return fail(AUTH_COPY.badPayload) }

    const uid = (body.uid ?? '').trim()                                        // ①
    const password = body.password ?? ''
    if (!UID_PATTERN.test(uid) || !password) return fail(AUTH_COPY.badCredentials, 401)   // ②

    // …限流检查（§4.4）…

    const user = await env.DB.prepare('SELECT uid, uname, password_hash, salt FROM user WHERE uid = ?')
        .bind(uid).first<{...}>()                                              // ③

    if (!user) return recordFail()                                             // ④ 用户不存在 → 和密码错走同一条路
    if (!safeEqual(await hashPassword(password, user.salt), user.password_hash)) return recordFail()   // ⑤

    // 成功：清限流 + 发 token
    await env.DB.prepare('DELETE FROM login_attempt WHERE uid = ?').bind(uid).run()   // ⑥
    const token = makeToken()
    await env.DB.prepare('INSERT INTO session (token, uid, created_at, expires_at) VALUES (?,?,?,?)')
        .bind(token, uid, now, now + SESSION_TTL).run()

    return json({ token, user: toPublicUser(user.uid, user.uname) })           // ⑦
}
```

**逐点**：

| # | 代码 | 知识点 |
|---|---|---|
| ① | `(body.uid ?? '').trim()` | 用户从 UI 复制 uid 时**极可能带上首尾空格** → 必须 trim（否则"看起来对却登不上"） |
| ② | `!UID_PATTERN.test(uid) \|\| !password` | **格式不对就直接走"账号或密码错误"**（401），**不单独提示"格式不对"** —— 少给攻击者信息；也省一次数据库查询 |
| ③ | `SELECT uid, uname, password_hash, salt` | **只取需要的列**（不用 `SELECT *`）；把 `password_hash`/`salt` 取出来是为了**在服务端比对** |
| ④ | `if (!user) return recordFail()` | **用户不存在也累加失败**（§4.4 ③）—— 防账号枚举 |
| ⑤ | `safeEqual(await hashPassword(password, user.salt), user.password_hash)` | **用库里的 salt 重算**，再**恒定时间比较**（§4.2/§4.3）；顺序是"新算的在前、库里的在后"（`safeEqual` 对顺序不敏感） |
| ⑥ | 成功后 `DELETE FROM login_attempt` | 清失败计数（§4.4） |
| ⑦ | `toPublicUser(user.uid, user.uname)` | **注意：用的是库里查出来的 uname**（不是请求里的），并把 hash/salt 挡在外面 |

**一句话对比 register 与 login**：
- register：**写两次**（user + session），要生成 id/盐；
- login：**读一次 → 算一次哈希 → 比较 → 写一次 session**，并在失败路径上写 `login_attempt`。
两者都在最后**回同样的结构** `{token, user}` —— **前端可以共用同一段"进入登录态"的逻辑**。

```ts
    const user = await requireUser(request, env)
    if (user instanceof Response) return user

    let body: { uname?: string }
    try { body = await request.json<{ uname?: string }>() } catch { return fail(AUTH_COPY.badPayload) }

    const uname = (body.uname ?? '').trim()
    if (!UNAME_PATTERN.test(uname)) return fail(AUTH_COPY.unameInvalid)

}
```

**三个知识点**：

3. **`WHERE uid = ?` 用的是 `user.uid`（来自 token），不是请求里的任何东西** —— **用户只能改自己**。
   > 铁律：**写接口的"主体"一律从 token 推导，绝不从 body 取**（否则就能改别人）。

**这段 `where` 很值得学（"可选条件 SQL 技巧"）**：

- `? = '' OR 条件` 实现"**参数为空时该条件自动失效**"：
  - 传空串 → `'' = ''` 为真 → 整行恒真（不过滤）；
  - 传了值 → 走真正的过滤。
- **好处**：**一条 SQL 覆盖四种组合**（全部公开 / 按作者 / 按关键字 / 两者都要），**不用在 JS 里拼 SQL 字符串**（拼字符串就有注入风险）。

**代价**：这种写法**索引利用会打折**（`? = ''` 让优化器难以判断），适合"数据量中等 + 查询灵活"的场景 —— **本项目正是这种场景**。数据量大了就要改成"按条件动态拼接 `where` 片段（片段本身是常量白名单）"。

**③ 出站前先算总数**：`counted` 与 `results` 是两条查询（§3.6），最后 `json({ items: results, total: counted?.n ?? 0 })`。

**④ `visibilityOf`：三态白名单**

```ts
/** 可见性白名单：只认三态常量，其它一律回落 public */
const visibilityOf = (raw: unknown): string =>
    raw === VISIBILITY.Private ? VISIBILITY.Private
        : raw === VISIBILITY.Protected ? VISIBILITY.Protected
            : VISIBILITY.Public
```

**知识点**：

- 入参类型写 `unknown`（**最安全的入参类型**：拿到手必须先判断才能用）；
- **任何不认识的值一律回落 `Public`** —— 关键是"**必须有一个明确、统一的回落策略**"：
  - 反面教材：直接把用户传的字符串存进去 → 数据库里出现 `'PRIVATE'`、`'私有'` 这类脏值，之后 `WHERE visibility = 'private'` 永远查不到它；
- 三态常量在**前端**也有一份（`src/constants/puzzle.ts` 的 `VISIBILITY` / `PUZZLE_VISIBILITY_COPY`）—— **两边引用同一处定义**才能保证不错位。

2. **为什么前端校验过还要再校验**：前端校验只是**体验**（即时提示）；**任何人都能绕过前端直接调接口**（curl / Postman）→ 服务端不校验 = 脏数据入库（之后列表页、游戏页会遇到"本不该出现的状态"）；
3. **`VALUES (?,?,?,?,?,?,?,?,?,0,0,?)`**：`show_solution` / `play_count` 写死为 0（新题默认"不公开答案、0 人玩"）→ 一共 **9 个 `?`**，与 `.bind(...)` 的 9 个参数一一对应。**数 `?` 与 `bind` 的个数是否相等，是读 SQL 时的基本功。**

### 5.6 精读 `puzzles/[pid].ts`（89 行，GET / PATCH / DELETE）

**① `load`：查一行 + 带上作者名**


**三个知识点**：

- **`?? null`**：`first()` 类型是 `Row | null`，这里再兜一次，保证调用方永远拿 `Row | null`（不会有 `undefined`）；
- **`Object.values(VISIBILITY) as readonly string[]`**：把三态常量对象转成数组用于 `includes` 校验；`as` 是因为 `Object.values` 推出来的类型偏窄（字面量联合），显式放宽成 `string[]` 才能接受"任意字符串"入参。

```ts
    return json({
        pid: row.pid, title: row.title, uname: row.uname, sideS: row.side_s,
        blankCount: row.blank_count, createdAt: row.created_at, puzzleText: row.puzzle,
        ...(withSolution ? { solutionText: row.solution } : {}),         // ④ 条件性字段
    })
}
```

| # | 做法 | 为什么 |
|---|---|---|
| ① | **`requireUser` 的失败被"降级"成 `null`**（不直接 return） | public/protected 题**不需要登录也能看** —— "没登录"是**正常情况**，不是错误 |
| ② | **private + 非作者 → 404 而不是 403** | **不泄露"这道题存在"**（否则别人能拿 pid 试探哪些有效） |
| ③ | **`show_solution === 1 \|\| row.uid === myUid`** | "公开答案"开关 + **作者特权**：作者永远能看到自己的答案（否则编辑时没法核对） |
| ④ | **`...(条件 ? { solutionText } : {})`** | 不满足时**这个 key 根本不存在**（不是 `undefined`、也不是空串）→ 前端用 `data.solutionText ?? null` 就能准确判断"服务端有没有下发答案" |

> **记住**：所谓"答案不公开"，不是"前端藏起来"，而是**服务端根本没发**。前端再怎么改代码也拿不到。**安全必须在服务端。**

**③ PATCH：作者改题（"动态 SET"技巧）**

```ts
const sets: string[] = []          // 要改的列片段
const vals: unknown[] = []         // 对应的参数值

if (body.title !== undefined) {
    const title = body.title.trim()
    if (!title || title.length > TITLE_MAX) return fail(`标题必填，1~${TITLE_MAX} 字符`)
    sets.push('title = ?'); vals.push(title)
}
if (body.visibility !== undefined) {
    if (!VIS_LIST.includes(body.visibility)) return fail('可见性取值不合法')
    sets.push('visibility = ?'); vals.push(body.visibility)
}
if (body.showSolution !== undefined) {
    sets.push('show_solution = ?'); vals.push(body.showSolution ? 1 : 0)     // 布尔 → 0/1
}
if (body.puzzleText !== undefined || body.solutionText !== undefined) {
    const checked = checkPuzzle(body.puzzleText ?? '', body.solutionText ?? '')
    if (checked instanceof Response) return checked
    sets.push('puzzle = ?', 'solution = ?', 'side_s = ?', 'blank_count = ?')
    vals.push(checked.puzzleText, checked.solutionText, checked.sideS, checked.blanks)
}
if (!sets.length) return fail('没有要修改的字段')

vals.push(row.pid)
await env.DB.prepare(`UPDATE puzzle SET ${sets.join(', ')} WHERE pid = ?`).bind(...vals).run()
```

**PATCH 的四个要点（"部分更新"的标准写法）**：

1. **每个字段都判断 `!== undefined`**（不是 `if (body.title)`）—— 因为**空字符串也是有效输入**：要能回"标题不能为空"，而不是"静默忽略这次修改"；
2. **`sets` 里放的全是"代码里写死的常量片段"**（`'title = ?'`），**值一律走 `vals` → `bind`** → **所以"动态拼接 SQL"依然安全**（拼的是结构，不是用户数据）；
3. **`vals` 的顺序必须与 `sets` 里 `?` 的顺序一一对应** —— 这是这种写法**唯一的心智负担**（列多时容易错位），所以本项目把"题面 + 答案"那一组**四个列一起推进去**，减少对不齐的机会；
4. **`body.showSolution ? 1 : 0`**：JS 布尔 → SQLite 的 0/1（§3.2 第 3 点）。

**④ DELETE：作者硬删 + 清游玩记录**

```ts
await env.DB.batch([
    env.DB.prepare('DELETE FROM puzzle_play WHERE pid = ?').bind(pid),
    env.DB.prepare('DELETE FROM puzzle WHERE pid = ?').bind(pid),
])
return json({ ok: true })
```

**知识点**：
- **先删子表（游玩记录）再删主表** —— 因为没有外键约束（§3.1），数据库不会替你清理；
- **`batch` 让两件事一起生效**（§3.3）；
- **`{ ok: true }`**：删除类接口不需要回数据，一个明确的成功标记就够。

### 5.7 精读 `puzzles/[pid]/play.ts`（31 行，热度计数）

```ts
/** 热度去重窗口：同一人 1 小时 1 次 */
const HOUR_MS = 3600_000

export const onRequestPost: PagesFunction<Env> = async ({ request, env, params }) => {
    const me = await requireUser(request, env)
    if (me instanceof Response) return me
    const pid = String(params.pid)

    const p = await env.DB.prepare('SELECT uid, play_count AS playCount FROM puzzle WHERE pid = ?')
        .bind(pid).first<{ uid: string; playCount: number }>()
    if (!p) return fail('题目不存在', 404)
    if (p.uid === me.uid) return json({ playCount: p.playCount, counted: false })   // ① 作者本人不计

    const now = Date.now()
    const last = await env.DB.prepare('SELECT played_at FROM puzzle_play WHERE pid = ? AND uid = ?')
        .bind(pid, me.uid).first<{ played_at: number }>()
    if (last && now - last.played_at < HOUR_MS) return json({ playCount: p.playCount, counted: false })   // ②

    await env.DB.batch([
        env.DB.prepare(
            `INSERT INTO puzzle_play (pid, uid, played_at) VALUES (?,?,?)
             ON CONFLICT(pid, uid) DO UPDATE SET played_at = excluded.played_at`,
        ).bind(pid, me.uid, now),
        env.DB.prepare('UPDATE puzzle SET play_count = play_count + 1 WHERE pid = ?').bind(pid),
    ])
    return json({ playCount: p.playCount + 1, counted: true })                     // ③
}
```

**四个知识点**：

| # | 做法 | 为什么 |
|---|---|---|
| ① | **作者自己玩不计热度** | 否则作者狂点自己的题就能刷榜 |
| ② | **1 小时窗口**（`now - last.played_at < HOUR_MS`） | 防"刷新页面刷热度"：同一人一小时内只计一次 |
| ③ | **返回 `counted` 布尔** | 前端要知道"这次到底算没算"（可以据此决定是否刷新热度显示），**同时**避免了"前端自己猜规则" |
| ④ | **`UPDATE ... play_count = play_count + 1`**（在数据库里自增） | **不要在 JS 里 `p.playCount + 1` 再写回去** —— 并发时会丢计数（两个请求都读到 5，都写 6，实际应该 7）。**"自增"必须交给数据库** |

**`batch` 里两句的顺序**：先 upsert 游玩记录，再给题目的 `play_count` 加一 —— 两者一起生效（§3.3）。

### 5.8 精读 `puzzles/mine/[rowId].ts`（21 行，作者态详情）

```ts
/** GET：作者态详情（一次拿全 pid + 题面 + 答案 + 状态；uname 供 MyPuzzleDetail extends PuzzleDetail） */
export const onRequestGet: PagesFunction<Env> = async ({ request, env, params }) => {
    const me = await requireUser(request, env)
    if (me instanceof Response) return me

    const row = await env.DB.prepare(
        `SELECT p.pid, p.row_id AS rowId, p.title, u.uname, p.side_s AS sideS,
                p.blank_count AS blankCount, p.visibility, p.show_solution AS showSolution,
                p.play_count AS playCount, p.created_at AS createdAt,
                p.puzzle AS puzzleText, p.solution AS solutionText
         FROM puzzle p JOIN user u ON u.uid = p.uid
         WHERE p.row_id = ? AND p.uid = ?`,
    ).bind(String(params.rowId), me.uid).first()

    if (!row) return fail('题目不存在或不可访问', 404)
    return json(row)
}
```

**三个知识点**：
1. **`WHERE row_id = ? AND uid = ?`（双条件）**：`rowId` 8 位、熵不如 pid，所以**再叠加"必须是我的"** —— 即使别人猜到了 rowId，也拿不到（因为 `uid` 不匹配）；
2. **作者态可以一次给全**（含 `solutionText` 与 `pid`）：因为**这是你自己的题**，没有"答案保密"的问题；这也是为什么"我的题目"页能直接进编辑；
3. **`return json(row)` 这里直接吐了 `row`** —— 注意：**它的 SELECT 列全是公开字段**（没有任何敏感列），所以安全。**这正是"手写字段列表"的价值**：只要列表干净，出站就干净。

| 操作 | 游客 | 登录用户 | 作者本人 |
|---|---|---|---|
