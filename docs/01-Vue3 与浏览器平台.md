## 1. Vue3 核心概念

### 1.1 知识点：声明式渲染（Vue 到底帮你干了什么）

**不用 Vue**：数据变了，你得自己找到 DOM 节点改它。
**用 Vue**：你只描述"**数据长这样时，页面长这样**"，数据一变，Vue 自己算最小改动去更新页面。

```html
<p>{{ infoText }}</p>          <!-- 数据变 → 这段文字自己变 -->
```

**本项目**：`GamePage.vue:49` `<p class="meta-line game-info">{{ infoText }}</p>` —— 页面从来不去"改 DOM"，只声明"这里显示 `infoText`"。

### 1.2 知识点：单文件组件（SFC）的三段

一个 `.vue` 文件 = 三种东西写在一起：

| 段 | 作用 | 本项目例 |
|---|---|---|
| `<script setup lang="ts">` | 逻辑（相当于"这个组件的 JS"）；**顶层声明的变量/函数自动暴露给模板** | `GamePage.vue:1-45` |
| `<template>` | 视图（HTML + 指令） | `GamePage.vue:47-78` |
| `<style scoped>` | 只作用于本组件的样式（Vue 会给元素加唯一属性，防串味） | `GamePage.vue:80-109` |

**编译后是什么**：`vite` 把它变成一个 JS 组件的 **setup 函数 + render 函数**（所以浏览器最终拿到的只有 JS/CSS，没有 `.vue`）。
**`<script setup>` 的意义**：不用再写 `export default { components: {...}, data() {...}, methods: {...} }` —— **顶层声明的东西模板里直接能用**（这就是为什么 `GamePage.vue` 里 `items`、`stepLabel`、`infoText` 在 template 里"凭空出现"）。

### 1.3 知识点：`ref` 与 `.value`（响应式的最小单位）

```ts
import { ref } from 'vue'
const count = ref(0)      // 一个"响应式盒子"，包着 0
count.value++             // 在 JS 里必须写 .value
```

```html
<p>{{ count }}</p>        <!-- 模板里 Vue 自动解包，不用写 .value -->
```

**为什么要有 `.value`**：JS 里基本类型（number/string）**没法被追踪变化**，只有"对象属性"能（Vue 用 Proxy 监听）。`ref` 就是一个对象，值放在它的 `.value` 里 —— 改 `.value` 就等于"改了对象的属性"，Vue 才知道。

**本项目（`src/composables/board/useZoom.ts:7-13`）**：

```ts
const zoom = ref<number>(clampZoom(initial))          // 响应式数字
const zoomIn = (): void => { zoom.value = zoomInOf(zoom.value) }    // 读 + 写都要 .value
const zoomOut = (): void => { zoom.value = zoomOutOf(zoom.value) }
```

**坑（两条，最常踩）**：
1. 忘写 `.value`：`zoom = zoomInOf(zoom)` → 你把变量本身指向了数字，**页面不会更新**（而且 TS 会报错，所以能拦住）；
2. 传出去以后别人改 `zoom.value` **你这边也能看到**（同一个盒子）→ 所以 `useZoom` 的返回值既是"数据"又是"唯一真源"。

### 1.4 知识点：`computed`（派生值 + 自动缓存）

**是什么**：`computed` 是"**由别的响应式数据算出来的值**"。特点：

- **自动追踪依赖**：依赖变了它才知道自己该变；
- **有缓存**：依赖没变，重复读它不会重算（`ref` 做不到这点）；
- 读的时候也要 `.value`（在 JS 里），模板里自动解包。

```ts
const a = ref(2)
const b = ref(3)
const sum = computed(() => a.value + b.value)    // a 或 b 变 → sum 自动变
```

**本项目（`GamePage.vue:24、30-44`，逐段）**：

```ts
/** 操作条：左段（返回/重开）＋ 右段（提示/参考答案/DEV 作弊）*/
const items = computed<Actions>(() => [...leadActions.value, ...trailActions.value])

/** 题目信息行 */
const infoText = computed<string>(() => {
    const meta = gameStore.meta
    if (meta.title) return `${meta.title} · ${meta.uname}`      // 挑战/自有题
    const s = gameStore.sudoku.S
    return `系统生成 ${s}×${s}`                                  // 系统题
})

/** 游玩盘：只传 board/boxSize/selected/conflictMask/zoom */
const boardParams = computed<BoardRenderInput>(() => ({
    board: gameStore.board,
    boxSize: gameStore.sudoku.B,
    selected: gameStore.selected,
    conflictMask: gameStore.conflictMask,
    zoom: zoom.value,
}))
```

**要看出三件事**：
1. 页面**不存数据**，只有"**派生视图数据**"（`items` / `infoText` / `boardParams`）—— 这就是"页面只接线"的字面含义；
2. `boardParams` 是一个**对象 computed**：任何一项变（含 `zoom.value`）→ 新对象 → 传给 `BoardView` 的 props 变 → 触发重绘（§3.5 会讲这条链）；
3. **所有分支都在 computed 里**（有标题显示标题、否则显示"系统生成 9×9"）→ 模板里只剩一句 `{{ infoText }}`，**判断逻辑集中**。

**坑**：`computed` 里**不要写副作用**（发请求、改别的数据）。它可能被多次求值、也可能根本不求值 —— 有副作用就不可预测。

### 1.5 知识点：`watch`（"某数据变了，我要做件事"）

```ts
watch(源, (新值, 旧值) => { /* 副作用 */ })
```

**和 `computed` 的分工**：`computed` = **算出值**；`watch` = **做事**（请求、重置、打日志、存盘）。

**本项目（`useZoom.ts:28-32`，逐行）**：

```ts
export const useBoardZoom = (boxSize: () => number) => {
    const state = useZoom(defaultZoomOf(boxSize()))
    watch(() => boxSize(), (next) => { state.resetZoom(defaultZoomOf(next)) })
    return state
}
```

**逐行解释**：
- 参数是 `boxSize: () => number` —— **传进来的不是数字，是"取数字的函数"**（为什么？§1.11 专门讲，这是本项目最重要的技巧之一）；
- `useZoom(defaultZoomOf(boxSize()))`：初始值 = 当前盘面大小对应的默认缩放（9 阶小、16 阶要缩小才放得下）；
- `watch(() => boxSize(), ...)`：**第一个参数是"取值函数"**（Vue 每次重算它来看有没有变），值一变就把缩放**复位**到新尺寸的默认值；
- **为什么要有这个 watch**：载入"16 阶大棋盘"时，盘面尺寸从"还没载入(0)"变成 16，缩放必须跟着复位；否则会保留上一个盘面的缩放，直接显示成"半个棋盘"。

**一句话**：`computed` 是"跟着算"，`watch` 是"变了就干"。

### 1.6 知识点：生命周期钩子（组件在什么时候做什么）

| 钩子 | 什么时候执行 | 能干什么 |
|---|---|---|
| `onMounted` | 组件**已经插入页面**（DOM 已存在） | 量元素尺寸、绑事件、初始请求、`new ResizeObserver` |
| `onBeforeUnmount` | 组件**即将销毁** | 清理（断连、清定时器、terminate Worker） |
| `onUnmounted` | 已销毁 | 一般用上面那个 |

**本项目两个真实例子**：

```ts
// useGameFlow.ts:90-98 —— 进游戏页时做一次"守卫 + 取一次性提示"
onMounted(() => {
    if (gameStore.mode !== GAME_MODE.Game || !gameStore.board.length) {
        router.replace({ name: PAGE.Difficulty })      // 数据不对（直接刷了 URL）→ 送回难度页
        return
    }
    const saved = puzzleStore.takeSavedTip()            // "提交到我的题目"成功的一次性轻提示
    if (saved) tip.value = saved
})
```

```ts
// useBoardCanvas.ts:41-49 —— 绑 ResizeObserver，并在卸载时断开
let ro: ResizeObserver | null = null
onMounted(() => {
    const box = boxEl.value            // ← 只有 mounted 之后 DOM 才存在，ref 才有值
    if (!box) return
    ro = new ResizeObserver(measure)
    ro.observe(box)
    measure()
})
onBeforeUnmount(() => { ro?.disconnect(); ro = null })   // ← 不清理会造成内存泄漏
```

**知识点**：`ref<HTMLCanvasElement | null>(null)` 这种"模板 ref"在 `onMounted` **之前是 `null`** —— 这就是为什么所有"操作 DOM"的代码都写在 mounted 里。

### 1.7 知识点：props（父 → 子）与 emit（子 → 父）

**规矩**：数据**向下流**（props），事件**向上发**（emit）。子组件**不许自己改父组件的东西**。

```html
<!-- 父 -->
<Child :title="t" @done="onDone" />
```
```ts
// 子：声明接收什么、能发出什么
const props = defineProps<{ title: string }>()
const emit = defineEmits<{ done: [] }>()
emit('done')
```

**本项目（`src/components/BoardView.vue:10-30`，逐段翻译）**：

```ts
const props = withDefaults(
    defineProps<{
        board: Board                                   // 必给：格子盘
        boxSize: number                                // 必给：宫宽（画粗线用）
        selected?: Position | null                     // 可选：选中格
        conflictMask?: ConflictMask                    // 可选：冲突标记
        zoom?: number                                  // 可选：缩放
        interactive?: boolean                          // 可选：可玩（接点击）还是只读预览
        zoomActions?: Actions                          // 可选：缩放按钮的数据
    }>(),
    { selected: null, zoom: BOARD_ZOOM.min, interactive: true },   // ← 缺省值
)

const emit = defineEmits<{ 'cell-click': [pos: Position] }>()      // 能发出的唯一事件
```

**逐点解释**：
1. **没有默认值的 props 必须给**（`board` / `boxSize`）；有默认值的可以不给；
2. `withDefaults` 就是"给可选 props 指定默认值"的官方写法；
3. `defineProps` / `defineEmits` 是**编译宏**（不需要 import，Vue 编译时处理）；
4. `emit('cell-click', pos)` 把"用户点了第 r 行 c 列"交给父组件 —— **BoardView 自己不知道点击该干什么**（它不碰 store，见 §1.12）；
5. 父组件接住它（`GamePage.vue:56`）：`@cell-click="gameStore.select"`。

### 1.8 知识点：`v-bind` 一次传一整个对象（本项目"传数据"的招牌动作）

```html
<Child v-bind="obj" />            <!-- 等价于 :a="obj.a" :b="obj.b" ... -->
<Child v-bind="obj" extra="1" />  <!-- 还能再补别的 -->
```

**本项目（`GamePage.vue:56、66`）**：

```html
<!-- 游玩盘：boardParams 是 computed 出来的对象，一次摊开成 props -->
<BoardView v-bind="boardParams" :zoom-actions="zoomActions" @cell-click="gameStore.select" />

<!-- 参考答案遮罩里的只读盘：换一份 computed 对象就行，组件一个字都不用改 -->
<BoardView v-bind="answerInput" :zoom-actions="answerZoomActions" />
```

**为什么这么做（很重要的设计）**：
- 同一块 `BoardView`，在**玩游戏**和**看答案**两处复用：差别只有"给哪份数据"；
- 想加一个渲染参数（比如"是否显示候选数"）→ 只改 `BoardRenderInput` 类型 + 两处 computed，**组件内部照样不变**；
- 页面里那两行长什么样，一眼就能看出"这个棋盘吃了哪些数据"。

### 1.9 知识点：模板里最常用的 8 个指令（对着 `GamePage.vue` 看）

| 写法 | 作用 | 本项目位置 |
|---|---|---|
| `{{ x }}` | 插值（显示文本） | `{{ infoText }}`（:49） |
| `:prop="x"` | 把**数据**绑给 prop/属性 | `:text="a.text"`（:52） |
| `@event="fn"` | 绑事件 | `@cell-click="gameStore.select"`（:56） |
| `v-for` + `:key` | 列表渲染（**必须给唯一 key**） | `v-for="a in items" :key="a.key"`（:52） |
| `v-if` / `v-else` | 条件渲染（**真的不渲染**，不是隐藏） | `<p v-if="tip">`（:54） |
| `:class="{...}"` | 按条件加类名 | `:class="{ 'is-interactive': interactive }"`（BoardView:48） |
| `v-on="{...}"` | **一次绑一组事件** | `v-on="interactive ? { click: onCanvasClick } : {}"`（BoardView:47） |
| `v-html` | 渲染 HTML | **本项目禁用**（XSS 风险，要显示文本就用 `{{ }}`） |

**三个值得细看的点**：

1. **`v-for` 的 `:key` 是"身份牌"**：Vue 靠它判断"这一项是上一轮的第几项"，缺了 key（或用数组下标当 key）会导致输入框内容错位之类的怪 bug。本项目一律用数据里的稳定 `key`（如 `a.key`）。
2. **`:class="{ 'is-interactive': interactive }"`**：对象写法 —— **键是类名、值是条件**。`BoardView.vue:133` 里 `.board-canvas.is-interactive { cursor: pointer }` 就是"只有可玩时才显示手型"。
3. **`v-if` 与 `v-show` 的区别**：`v-if` 是"根本不渲染这段 DOM"，`v-show` 是"渲染了但用 CSS 隐藏"。本项目 `tip` / `Overlay` 都用 `v-if` / `:show`（`Overlay` 内部处理），因为"没提示就不该有那个元素"。

### 1.10 知识点：插槽（slot）——"组件留个洞，父组件往里塞东西"

```html
<!-- 子组件模板里 -->
<div class="modal"><slot /></div>
<!-- 父组件用法 -->
<MyModal><p>塞进来的内容</p></MyModal>
```

**本项目（`GamePage.vue:64-73`，逐段）**：

```html
<!-- 参考答案遮罩：按钮条 + 文本由 Overlay 渲染，「里面放什么」由父组件用插槽给 -->
<Overlay :show="answerOpen" :text="answerTitle" :actions="answerActions">
    <BoardView v-bind="answerInput" :zoom-actions="answerZoomActions" />
</Overlay>

<!-- 导出遮罩：wide 加宽；说明文字用 desc；插槽里是「小标题 + 只读文本框」 -->
<Overlay :show="exportOpen" wide :text="EXPORT_COPY.title" :desc="exportTip" :actions="exportActions">
    <p class="export-label">{{ EXPORT_COPY.puzzleLabel }}</p>
    <textarea class="input textarea export-text" readonly :value="exportPuzzleText"></textarea>
</Overlay>
```

**为什么要插槽**：`Overlay`（遮罩）的**壳**（半透明背景、居中、关闭按钮、标题、按钮条）是固定的，但**中间放什么**天差地别（有时放棋盘、有时放文本框）。
→ 用插槽把"可变部分"交给调用方，**一个 Overlay 服务所有弹窗**（这比写 5 个弹窗组件更好维护）。

**细节**：`textarea` 用 `:value` 而不是 `v-model` —— 只读展示不需要双向绑定（`v-model` 会带一个监听器，那是浪费）。

### 1.11 ⚠️ 响应式的三个大坑（都在这份代码里真实出现过、被绕开的）

**坑 1：解构丢了响应式**

```ts
const store = useGameStore()
const { board } = store          // ❌ board 只是"当时那一刻的数组"，之后 store 变了它不知道
```
✅ 正确：**用 `store.board` 直接读**，或 `storeToRefs(store)`（Pinia 提供）。本项目一律"**谁要谁现读**"。

**坑 2：把"值"传进去，函数就永远拿到旧值 → 所以要传"取值函数"**

```ts
// useBoardZoom 的签名（useZoom.ts:28）
export const useBoardZoom = (boxSize: () => number) => { ... }
```

如果写成 `useBoardZoom(boxSize: number)`：
- 页面第一次渲染时值可能是 `0`（棋盘还没载入）→ 之后变成 16，**函数里的 `boxSize` 永远是 0**；
- 因为它拿到的只是"一个数字的拷贝"，没有任何追踪能力。

**传函数（`() => number`）就不同**：每次调用都**现读**，于是 `watch(() => boxSize())` 能追踪到 store 里的变化。
本项目里同款写法：
- `useBoardZoom(() => gameStore.config.boxSize)`（`GamePage.vue:16`）
- `useBoardCanvas(canvasEl, boxEl, () => props, pos => emit('cell-click', pos))`（`BoardView.vue:30`）—— 把 **props 整体**用函数传，保证每次重绘读到的都是最新 props。

**口诀：**"**跨层传响应式数据，传盒子（ref/computed）或传取值函数；别传快照值。**"

**坑 3：`.value` 在模板里不写、在 JS 里必须写**

```html
<BoardView v-bind="boardParams" />       <!-- 模板：自动解包 -->
```
```ts
const boardParams = computed(() => ({ ... zoom: zoom.value }))   // JS：必须 .value
```
判断口诀：**"在 `<template>` 里不写，在 `<script>` 里写"**。

### 1.12 把这些串起来：为什么"页面只接线"

回看 `GamePage.vue` 的 7 个声明（§CODE-GUIDE 4.0 有同一张表）：页面做的全是"**取数据 → 组合 → 摆给组件**"：

```ts
const gameStore = useGameStore()                                    // ① 数据源
const { zoom, zoomActions } = useBoardZoom(() => gameStore.config.boxSize)   // ② 缩放
const { tip, answerOpen, ..., leadActions, trailActions, ... } = useGameFlow()  // ③ 流程
const items = computed(...)                                          // ④ 拼按钮条
const stepLabel = (i: number): string => `${i}步`                    // ⑤ 纯展示回调
const infoText = computed(...)                                       // ⑥ 信息行
const boardParams = computed(...)                                     // ⑦ 渲染入参
```

**逻辑去哪了**：`useGameFlow()`（组合式函数，§06 册）。它内部才用 `router`、`gameStore.jumble`、`hintTextOf` 等等。
**守卫 R6 的三条硬要求**（声明 ≤10 / 禁 `Math.` / 不许 import `core`·`services`·`render`）就是用来**守住这个结构**：只要守卫绿，页面一定薄。

## 2. Pinia（状态管理）：为什么需要"共享的响应式盒子"

### 2.1 知识点：没有 Pinia 会怎样

假设"登录态"要同时被顶栏、页面、路由守卫用。两种笨办法：

- **props 层层传**：`App → Layout → Header → Avatar`，中间层被迫携带与自己无关的数据（"prop 钻透"）；
- **各自 `ref`**：每个组件存一份 → **多个副本不一致**（一个登出了，另一个还以为登录着）。

**Pinia 提供的**：一个**全局唯一且响应式的对象**。谁 `useUserStore()` 拿到的都是**同一个实例**（同一批 ref）→"一处改、处处变"。

### 2.2 知识点：setup 风格的 store（本项目唯一的写法）

```ts
export const useUserStore = defineStore('userStore', () => {
    const profile = ref<User | null>(null)            // 状态
    const isGuest = computed(() => !profile.value)    // 派生
    const login = async (p: LoginPayload) => { ... }  // 动作
    return { profile, isGuest, login }                // ← 要用的都必须 return 出去
})
```

**看出它和组件像在哪**：`defineStore(名字, () => {...})` 里写的东西与 `<script setup>` 几乎一样（`ref` / `computed` / 函数），**只是没有模板**。所以会写组合式组件，就会写 Pinia。

### 2.3 本项目逐段（`src/stores/user.ts`，全文只有 39 行）

```ts
export const useUserStore = defineStore('userStore', () => {
    const profile = ref<User | null>(null)                     // ① 唯一真源
    const isGuest = computed<boolean>(() => !profile.value)     // ② 派生，不另存布尔字段
    const uname = computed<string>(() => profile.value?.uname ?? '')
    const uid = computed<string>(() => profile.value?.uid ?? '')

    /** 401（token 过期）时 client 已清 token → 这里同步把登录态置空 */
    onUnauthorized(() => { profile.value = null })              // ③ 与 HTTP 层"事件"接线

    const register = async (payload: RegisterPayload): Promise<void> => {
        profile.value = (await apiRegister(payload)).user        // ④ 请求 → 直接写进真源
    }
    const login = async (payload: LoginPayload): Promise<void> => {
        profile.value = (await apiLogin(payload)).user
    }
    const logout = async (): Promise<void> => {
        try { await apiLogout() } finally { profile.value = null }   // ⑤ 请求失败也必须本地登出
    }
    /** 刷新后静默恢复（无 token 不发请求）；同一时刻只发一次 —— 路由守卫可 await 它再判登录态 */
    let pending: Promise<void> | null = null
    const restore = (): Promise<void> => (pending ??= (async () => {   // ⑥ 并发去重
        try { profile.value = await apiMe() } catch { profile.value = null }
    })())
```

**六个点，每个都是一个通用知识点**：

| # | 做法 | 背后的概念 |
|---|---|---|
| ① | 只存一个 `profile`，其它全靠派生 | **单一事实来源**：能算出来的别存 |
| ② | `isGuest` / `uname` / `uid` 都是 `computed` | **派生数据不进 store**，否则要手动同步多个字段（经典 bug 温床） |
| ③ | `onUnauthorized(...)` 在 store 加载时注册 | **观察者模式**：HTTP 层遇 401 → 通知所有关心的人（见 08 册 `client.ts`） |
| ④ | 请求返回值**直接赋给真源** | 不做"提交后再查一次接口"的多余往返 |
| ⑤ | `try ... finally` | **本地状态必须与远端一致**：即使请求失败也要清本地 |
| ⑥ | `pending ??=` 缓存同一个 Promise | **幂等 + 并发去重**：多处同时调用只发一次请求，后来者 await 同一个 Promise |

**⑥ 是这份代码最"高级"的一处写法**，展开讲：

```ts
let pending: Promise<void> | null = null
const restore = (): Promise<void> => (pending ??= (async () => { ... })())
```

- `pending ??= X`：**只有 `pending` 是 `null`/`undefined` 时才求值 `X` 并赋给它**（"空值赋值"运算符）；
- `X` 是"立刻执行的 async 函数"（`(async () => {...})()`）→ 结果是 Promise；
- 所以**第一次调用**真的发请求、并把 Promise 存起来；**之后每次调用**直接返回**同一个 Promise**；
- 效果：`restore()` 全站只发一次请求，但**任何人都能 `await restore()`**等待它完成 —— 这正是"路由守卫可以 `await` 它再判断登录态"的前提。

### 2.4 什么数据配进 store（判据；详细版见 05 册）

| 数据 | 放哪 | 本项目实例 |
|---|---|---|
| 跨页面共享 + 需要响应式 | **store** | 当前棋盘 `gameStore.board`、登录态 `userStore.profile` |
| 只在某一个流程内用 | **composable 的 `ref`** | 参考答案遮罩开关 `answerOpen`、提示文案 `tip`（`useGameFlow.ts:26`） |
| 纯 UI 偏好（刷新要保留） | localStorage（`services/prefs.ts`） | 登录 token、上次登录账号 |
| 能算出来的 | **都不存**，用 `computed` | `infoText`、`isGuest`、页数 |

**反例**（本项目禁止）：把 `answerOpen` 塞进 `gameStore` —— 它是"某一次交互的临时状态"，放进全局只会让 store 臃肿、并被无关页面误读。

### 2.5 坑：从 store 解构会丢响应式（与 §1.11 坑 1 同源）

const { board, selected } = useGameStore()       // ❌ 拿到的是快照

### 3.1 知识点：DOM、模板 ref 与"点在哪一格"

**问题**：用户点了画布，怎么知道是第几行第几列？

```ts
// BoardView.vue:27-30
const canvasEl = ref<HTMLCanvasElement | null>(null)      // ① 模板 ref：指向真实 <canvas>
const boxEl = ref<HTMLElement | null>(null)
const { onCanvasClick } = useBoardCanvas(canvasEl, boxEl, () => props, pos => emit('cell-click', pos))
```
```html
<canvas ref="canvasEl" ... />          <!-- ② 模板里 ref="canvasEl" 与上面的变量同名即绑定 -->
```

```ts
// render/board.ts:117-121 —— 点击坐标 → 行列
export const getClickPos = (canvas: HTMLCanvasElement, e: MouseEvent, size: number): Position | null => {
    const rect = canvas.getBoundingClientRect()
    if (!rect.width) return null
    return offsetToCell(e.clientX - rect.left, e.clientY - rect.top, rect.width, size)
}
```

**三个必须懂的坐标系**：

| 术语 | 含义 |
|---|---|
| `e.clientX / clientY` | 鼠标在**浏览器视口**里的坐标（像素） |
| `canvas.getBoundingClientRect()` | 该元素在**视口**里的矩形（`left/top/width/height`） |
| 两者相减 | 得到"**在这个元素内部**的偏移" |

再把这个偏移按 `边长 / 格数` 换算成行列（`offsetToCell` 在 `core/board/metrics.ts` —— 纯计算，所以归 core）。

**坑**：
- **别用 `offsetX`**（受内部元素与 CSS 缩放影响，容易偏）；
- `rect.width === 0`（还没渲染 / 被隐藏）要早退 —— 本项目 `if (!rect.width) return null` 就是防这个；
- 页面滚动**不用额外处理**：`clientX` 与 `getBoundingClientRect()` 都在视口坐标系，相减天然抵消滚动。

### 3.2 知识点：为什么棋盘用 canvas 而不是 DOM 表格

| | DOM 网格（div/table） | **canvas** |
|---|---|---|
| 节点数 | 16 阶 = 256 格 × (格 + 数字 + 边框/选中框) → 上千节点 | **1 个** `<canvas>` |
| 更新一步 | Vue 要 diff 上千节点 | 一次 `renderBoard()` 重画 |
| 交互 | 每格单独绑事件（省事） | 自己算坐标（`getClickPos`） |
| 样式 | 交给 CSS | 全部自己画（颜色/字体/线宽 = `constants/board.ts`） |
| 可访问性 | 天然语义 | 需要额外处理 |

**本项目的选择**：**棋盘用 canvas**（重、要频繁重绘），**其它一切都是普通 DOM**（信息行、按钮、分页、遮罩）。
**代价必须认**：canvas **没有响应式** —— 数据变了它自己不变，**必须我们主动重画**（§3.5 的 `watchEffect` 就干这个）。

**canvas 2D 的最小 API 表（本项目用到的全部）**：

|---|---|---|
| `canvas.getContext('2d')` | 取画笔 | `render/board.ts` 的 `prepareCanvas` |
| `ctx.fillStyle` + `fillRect` | 填色（格底/白底） | `render/paint.ts`（格底）、`board.ts` 的 `paintBoard`（白底） |
| `ctx.font` + `fillText` | 画数字 | `render/paint.ts` 的 `paintCell` |
| `ctx.strokeStyle` + `lineWidth` + `strokeRect` | 画选中框 | :79-82 |
| `ctx.beginPath` / `moveTo` / `lineTo` / `stroke` | 画网格线 | :88-107 |
| `ctx.clearRect` | 擦干净 | :111 |
| `ctx.setTransform(dpr,0,0,dpr,0,0)` | 高清屏缩放（§3.3） | :36 |

### 3.3 知识点：`devicePixelRatio`（为什么高清屏要"画两次大"）

**问题**：CSS 里写 `width: 400px` 的元素，在"设备像素比 = 2"的屏幕上**实际占 800 个物理像素**。
如果你只给 canvas 400×400 的像素，浏览器就把它**拉伸**到 800 → 线条发虚、文字发糊。

**解法（三步，本项目 `setupCanvas` 就是这么写的）**：

```ts
// render/geometry.ts 的 boardGeometryOf + render/board.ts 的 prepareCanvas（逐行）
const dpr = window.devicePixelRatio || 1
const width = contentWidth ?? measureContentWidth(parent)   // 容器内容宽（CSS 像素）
const side = boardSideOf(width, zoom)                       // 棋盘边长（CSS 像素）
const pixel = Math.round(side * dpr)                        // ← ① 物理像素 = CSS 像素 × dpr

if (canvas.width !== pixel) { canvas.width = pixel; canvas.height = pixel }   // ② 改"像素尺寸"
canvas.style.width = `${side}px`                            // ③ 改"CSS 尺寸"（两者必须分别设）
canvas.style.height = `${side}px`

const ctx = canvas.getContext('2d')
ctx.setTransform(dpr, 0, 0, dpr, 0, 0)                      // ④ 之后所有绘制坐标按 CSS 像素写
ctx.textAlign = 'center'
ctx.textBaseline = 'middle'
```

**要理解的三件事**：
1. **`canvas.width`（像素尺寸）与 `canvas.style.width`（CSS 尺寸）是两回事** —— 只设一个就会变形/模糊；
2. `ctx.setTransform(dpr,0,0,dpr,0,0)` = "把坐标系整体放大 dpr 倍"，之后你写 `fillRect(0,0,cellSize,cellSize)` 就能用**逻辑像素思考**，不用到处乘 dpr；
3. `if (canvas.width !== pixel)` 这个判断是**性能优化**：给 `canvas.width` 赋值会**清空画布并重置状态**，尺寸没变就别白干。

### 3.4 知识点：`ResizeObserver` 与"布局反馈循环"（本项目一个很真实的坑）

**是什么**：`ResizeObserver` 是浏览器提供的"**元素尺寸变化就通知我**"的监听器（比监听 `window.resize` 精准：只关心这个元素）。

```ts
// useBoardCanvas.ts:31-49（逐行）
const measure = (): void => {
    const box = boxEl.value
    const width = box ? measureContentWidth(box) : 0
    if (width !== contentWidth.value) contentWidth.value = width    // 变了才写（避免无意义重绘）
}

let ro: ResizeObserver | null = null
onMounted(() => {
    const box = boxEl.value
    if (!box) return
    ro = new ResizeObserver(measure)
    ro.observe(box)
    measure()                                        // 首帧手动量一次（不等回调）
})
onBeforeUnmount(() => { ro?.disconnect(); ro = null })
```

**这里藏着本项目的救命注释（`BoardView.vue:28`）**：

> 外层滚动框：**量它**（canvas 的直接父级会随棋盘收缩，量它会把当前宽度当上限）

**什么意思**：如果去量 `canvas` 的**直接父级**，那个父级的宽度**是由 canvas 决定的**（`display:flex` + 内容宽度）。
于是形成循环：**量到的宽度 → 决定棋盘大小 → 棋盘大小 → 又决定父级宽度** → 棋盘会越缩越小（或被锁死在上一次的宽度）。
**解法**：量**外面的滚动容器**（`.board-scroll-container`，宽度由页面决定、与棋盘无关），把"参考宽度"与"被决定的宽度"分开。

**通用知识点（一定要带走）**：
> **当"测量结果"会影响"被测量的元素"时，就会形成反馈循环 —— 必须改为测量一个"外部且稳定"的参照物。**

同类坑还有：用 `ResizeObserver` 监听"会被自己回调改变尺寸的元素"→ 触发"ResizeObserver loop limit exceeded"。

### 3.5 知识点：`watchEffect`（自动收集依赖）与"重绘链"

**`watch` 与 `watchEffect` 的区别**：

| | `watch(源, cb)` | `watchEffect(fn)` |
|---|---|---|
| 依赖怎么来 | **你显式写出**要观察的源 | **自动**收集：`fn` 里读过的响应式数据都算 |
| 什么时候跑 | 源变化时跑 cb（不立即） | **立即跑一次**，之后依赖变化就重跑 |
| 适合 | "A 变了做 B"（意图明确） | "把所有依赖都画出来"（重绘/同步类） |

**本项目（`useBoardCanvas.ts:20-38`，逐行）**：

```ts
/** 按当前入参重绘；缺省值由 renderBoard 兜底 */
const draw = (): void => {
    // 先读一遍依赖，保证 watchEffect 建立追踪（哪怕本次提前返回）
    const canvas = canvasEl.value
    const { board, boxSize, selected, conflictMask, zoom } = input()
    if (!canvas || !board.length) return

    renderBoard(canvas, { board, boxSize, selected, conflictMask, zoom }, contentWidth.value || undefined)
}

// canvas / 棋盘 / 选中 / 冲突 / zoom / 容器宽 任一变化自动重绘；随组件卸载自动停止
watchEffect(draw)
```

**这段注释为什么重要（超级常踩的坑）**：
`watchEffect` 靠"**执行时读了谁**"来决定观察谁。如果写成：

```ts
const draw = (): void => {
    if (!canvasEl.value) return            // ❌ 提前返回时，后面的 board/zoom 都没被读到
    const { board, zoom } = input()
    ...
}
watchEffect(draw)
```

那么**当 canvas 还没挂载时**，这次的依赖收集里**只有 `canvasEl`** —— 首次跑完就"只盯着 canvas"。
接下来即使 board 更新了也不会触发重绘，**除非**你的代码**每次执行都把要追踪的依赖读一遍**（本项目就是先读再判断）。
**结论**：`watchEffect` 的副作用函数里，**要追踪的依赖必须"在任何分支之前"读到**。

**这条"重绘链"（把前面所有知识点串起来）**：

```
用户点格子
  → GamePage 模板 @cell-click → gameStore.select(pos)      （§1.7 事件向上、store 动作）
  → store 里 selected 变                                     （§2 Pinia 响应式）
  → GamePage 的 boardParams computed 重算（含 selected）      （§1.4 派生）
  → <BoardView v-bind="boardParams"> 的 props 变              （§1.8 对象展开）
  → BoardView 传的是 () => props（取值函数）→ 重绘时读到新 props（§1.11 坑 2）
  → watchEffect(draw) 命中 → renderBoard(...)                （本节）
  → canvas 重画（选中框画在新格子上）                          （§3.2/3.3）
```

**记住这条链**，你以后遇到"点了没反应"就能一段一段排查（是 store 没变？computed 没重算？props 没传下去？还是 canvas 没重画？）。

**为什么这里不能靠模板响应式**：`<canvas>` 在 Vue 眼里只是"一个空元素"，它里面**没有一个 DOM 是 Vue 管的** —— 所以必须"数据变 → 手动重画"。

### 3.6 知识点：`localStorage`（"小本子"）与它的三个坑

**是什么**：浏览器提供的**按域名隔离**的键值存储。特点：

- **只能存字符串**（存对象要 `JSON.stringify`）；
- **同步 API**（会阻塞主线程，别存大东西）；
- **容量约 5MB**；
- **持久**（关浏览器还在），除非用户清数据。

**本项目（`src/services/prefs.ts` 全文，13 行）**：

```ts
/**
 * 纯 UI 偏好的本地存储（与 api/session.ts 同规则）
 * 键名统一 sudoku. 前缀；隐私模式下 localStorage 可能抛错 → 全部包一层
 */
const PREFIX = 'sudoku.'

export const readPref = (key: string): string => {
    try { return localStorage.getItem(PREFIX + key) ?? '' } catch { return '' }
}
export const writePref = (key: string, value: string): void => {
    try { localStorage.setItem(PREFIX + key, value) } catch { /* 忽略 */ }
}
export const clearPref = (key: string): void => {
    try { localStorage.removeItem(PREFIX + key) } catch { /* 忽略 */ }
}
```

**三个必须学的做法**：

1. **统一前缀 `sudoku.`**：同一个域名下可能有别的应用（你这个工作区里还有 `todo/`），前缀避免键名撞车；
2. **`try/catch` 包住每一个调用**：**浏览器隐私模式 / 禁用存储时，`localStorage` 的访问会直接抛异常**（不是返回 null！）。不包起来 = 整个应用白屏；
3. **缺省值用 `?? ''`**：读不到时返回空字符串，调用方不用处理 `null`。

**谁在用（`src/services/api/session.ts`）**：

```ts
const TOKEN_KEY = 'token'
const UID_KEY = 'lastUid'
export const getToken = (): string => readPref(TOKEN_KEY)
export const setToken = (token: string): void => writePref(TOKEN_KEY, token)
export const clearToken = (): void => clearPref(TOKEN_KEY)
export const getLastUid = (): string => readPref(UID_KEY)      // 登录页预填账号
export const setLastUid = (uid: string): void => writePref(UID_KEY, uid)
```

**注意它只放两样东西**：**会话 token** 与**上次登录的账号 ID**（为了登录页预填）。**绝不放密码**（本项目密码只发给后端校验，见 02 册哈希）。
**安全常识**：`localStorage` 的内容**同一个域下的 JS 都能读到**（XSS 会偷 token）→ 所以 token 的设计要能"**过期 + 服务端可作废**"（本项目后端就是这么做的）。

### 3.7 知识点：Web Worker（"另开一条线程算题"）

**问题**：JS 在浏览器里**只有一个主线程**。生成一道 16 阶数独要跑几十万次回溯 —— 在主线程序里跑，**页面会直接卡死（连"加载中"都转不起来）**。

**Web Worker 解决的**：另开一条**独立线程**跑 JS。特点：

| | 主线程 | Worker 线程 |
|---|---|---|
| 能碰 DOM 吗 | 能 | **完全不能** |
| 能用 `window` 吗 | 能 | 不能（有自己的全局环境） |
| 怎么通信 | — | `postMessage` 发 / `onmessage` 收（**结构化克隆**，不能传函数/DOM 节点） |

**这个限制反而成了我们的优势**：Worker 里**只能放纯计算** —— 正好就是 `src/core/**`（它不碰 DOM、不碰 store）。所以 core 能被**三个地方复用**：浏览器主线程 / Worker / 后端（见 02 册）。

**本项目（`src/services/sudoku/workerClient.ts`，逐段）**：

```ts
const runInWorker = <Res>(req: WorkerRequest, timeoutMs: number, timeoutCopy: string, failCopy: string): Promise<Res> => {
    return new Promise((resolve, reject) => {
        let settled = false                                  // ① "只结算一次"的闸门
        let timer: ReturnType<typeof setTimeout> | null = null
        let worker: Worker | null = null

        /** 清理资源（定时器、Worker） */
        const cleanup = (): void => {
            if (timer) clearTimeout(timer)
            worker?.terminate()                              // ② 线程用完就杀掉
            worker = null
        }

        const finish = (data: Res): void => {
            if (settled) return                              // ③ 已经结算过 → 什么都不做
            settled = true
            cleanup()
            resolve(data)
        }

        /** 失败：只 reject 一次 */
        const fail = (msg: string): void => {
            if (settled) return
            settled = true
            cleanup()
            reject(new Error(msg))
        }

        try {
            worker = new Worker(new URL('./worker.ts', import.meta.url), { type: 'module' })   // ④
        } catch {
            fail(failCopy)                                   // 浏览器不支持 Worker → 直接失败
            return
        }

        timer = setTimeout(() => { fail(timeoutCopy) }, timeoutMs)      // ⑤ 超时兜底

        worker.onmessage = (e: MessageEvent<GenerateResponse | SolveResponse>) => {
            if (e.data.ok) finish(e.data.result as Res)      // ⑥ 成功回包
            else fail(e.data.error || failCopy)              //    失败回包（如"这盘无解"）
        }

        worker.onerror = () => { fail(failCopy) }            // ⑦ Worker 内部抛异常

        worker.postMessage(req)                              // ⑧ 派发任务
    })
}
```

**八个点逐个解释**：

| # | 代码 | 为什么必须这样 |
|---|---|---|
| ① | `let settled = false` | 一个 Promise **只能结算一次**；而这里有**三条路**可能先到（超时 / 出错 / 回包），必须用闸门防止"第二次 resolve 无效"和"重复清理" |
| ② | `worker.terminate()` | Worker 里的**死循环/长计算只能用 terminate 掐断**；thread 不杀会常驻内存 |
| ③ | `if (settled) return` | 比如：回包先到、随后定时器才触发 → 第二次会被拦掉 |
| ④ | `new Worker(new URL('./worker.ts', import.meta.url), { type: 'module' })` | **Vite 能静态识别的写法**：`new URL('./worker.ts', import.meta.url)` 让打包器知道"这是一个独立的 worker 入口，要单独打一个 chunk"；写字符串路径它是认不出来的。`type:'module'` 因为源码是 ESM |
| ⑤ | `setTimeout(...)` + `timeoutMs` | 兜底：Worker 卡死时不会永远等（生成 15s、求解 15s，值在 `constants` 里） |
| ⑥ | `e.data.ok ? ... : ...` | **回包是一个判别联合**（`{ ok: true, result }` / `{ ok: false, error }`），TS 靠 `ok` 收窄类型 |
| ⑦ | `onerror` | Worker 脚本本身报错（如语法错误）时走这里 |
| ⑧ | `postMessage(req)` | 把 `{ kind: 'generate', boxSize, blanks }` 或 `{ kind: 'solve', board, maxSolutions }` 发过去 |

**两个设计决定（都很关键）**：

1. **每次调用 `new Worker`，用完就 `terminate` —— 不复用**。
   - 好处：**没有跨任务的残留状态**；超时后能**立刻**杀掉；实现简单；
   - 代价：新建线程有一次性开销（几十毫秒）—— 对"生成/求解"这种几百毫秒起步的任务完全划算。
2. **文案从常量传进来**（`SOLVE_COPY.timeout`、`'生成超时，请重试'`）而不是写死在客户端逻辑里 —— 保持"**文案集中一处**"。

**调用方长这样（`workerClient.ts:65-79`）**：

```ts
export const generateInWorker = (boxSize: number, blanks: number, timeoutMs = DEFAULT_TIMEOUT): Promise<PuzzleData> =>
    runInWorker<PuzzleData>({ kind: 'generate', boxSize, blanks }, timeoutMs, '生成超时，请重试', '生成失败，请重试')

export const solveMultiInWorker = (board: NumBoard, maxSolutions: number, timeoutMs = SOLVE_TIMEOUT): Promise<NumBoard[]> =>
    runInWorker<NumBoard[]>({ kind: 'solve', board, maxSolutions }, timeoutMs, SOLVE_COPY.timeout, SOLVE_COPY.fail)
```

**注意泛型 `<Res>`**：一个通道（`runInWorker`）服务两种任务，靠调用处写 `runInWorker<PuzzleData>(...)` / `runInWorker<NumBoard[]>(...)` 决定返回类型 —— 这正是 §4.9（00 册）泛型的实际用法。

### 3.8 知识点：`import.meta.env.DEV`（"只在开发环境存在"的代码）

```ts
// useGameFlow.ts:80-82
...(import.meta.env.DEV
    ? [{ key: 'cheat', text: '⚡ 作弊', onClick: gameStore.cheat }]
    : []),
```

- `import.meta.env` 是 **Vite 注入的构建期常量**（不是运行期读环境变量）；
- `DEV` 在 `pnpm dev` 时为 `true`、`pnpm build` 时为 `false`；
- 关键点：**打包时会被替换成字面量 `true`/`false`**，然后**压缩器会把整段死代码删掉** —— 所以**生产产物里根本没有"作弊"按钮的代码**（不是"隐藏了"，是不存在）。

**顺带看这段的写法**：`...(条件 ? [一项] : [])` —— 用数组展开实现"**条件性地往按钮条里加一项**"，比"if 里 push"更函数式（得到的是新数组，不改别人）。

### 3.9 性能知识点小结（这份代码里"为了不卡"做的所有事）

| 做法 | 位置 | 解决什么 |
|---|---|---|
| 把重计算扔进 Worker | `workerClient.ts` | 主线程不卡（否则 16 阶生成会冻结页面） |
| 容器宽度**只量一次**存进 ref | `useBoardCanvas.ts:18、31-35` | 避免每次重绘都读布局 → **强制同步布局（reflow）**；注释写得很清楚："重绘路径不再读布局" |
| `canvas.width` 变了才赋值 | `render/board.ts` 的 `prepareCanvas` | 赋值会清空画布并重置状态，别白做；**同时把 `resized` 返给调用方**（局量重绘据此退回整盘） |
| `width !== contentWidth.value` 才写 | `useBoardCanvas.measure` | 避免"值没变也触发重绘" |
| 只用一次 `getComputedStyle` | `measureContentWidth`（`render/geometry.ts`） | `getComputedStyle` 是昂贵的 |
| 统一线宽/颜色常量 | `constants/board.ts` | 一次调一次，不在循环里反复算 |
| 大数组用 `Uint8Array` | `generator.ts` | 内存与速度（00 册 §3.10） |
| 请求去重（`pending ??=`） | `stores/user.ts` | 避免刷新时并发发三次 `/me` |

**顺带记一个术语**：**reflow（回流/重排）** = 浏览器为了回答"这个元素多宽"，被迫重新计算布局。**读布局属性**（`clientWidth`、`getBoundingClientRect`、`getComputedStyle`）之后**又改样式**，就会触发"**读写交替 → 反复重排**"，长列表/动画里非常容易出现卡顿。
**规避口诀**：**"先集中读、再集中写"**；本项目更进一步 —— **把"读"从"每次重绘"里彻底拿出去**（只在 ResizeObserver 回调里读）。

### 3.10 路由（`vue-router`）在这里的角色（一句话版，详见 08 册）

- `router/index.ts` 里每个页面用 `component: () => import('@/pages/...')`（**懒加载**：进那条路由才下载那个 chunk）；
- 路由表用 `PAGE.*`（§00-4.3 的字面量类型）避免拼错；
- 跳转用 `router.replace`（不留历史，如登录成功）/ `router.back`（回上一页，如"返回"按钮：`useGameFlow.ts:54-57` 先看有没有历史，否则回难度页）。
